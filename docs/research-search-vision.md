# 連環（Renkan）— 個人研究の記憶を横断する探索基盤

## この文書について

本書は、Marginalis の次期仕様を定める文書ではない。**連環（Renkan）**と呼ぶ個人研究の
探索基盤について、何を実現したいのか、なぜそれが必要だと考えるのか、どのような原則を
守りたいのかを記したポジションペーパーである。

ここで述べる構想は Marginalis に閉じない。Marginalis は、この構想を現実の利用を通して検証する
最初のデータソースである。第一歩として Marginalis のノートをあいまい検索できるようにするが、
最終的に作りたいものはノートアプリケーションの検索機能ではない。研究活動の過程で複数の場所へ
分散した記録を、出典と文脈を失わずに横断できる個人研究の探索基盤である。

現行 Marginalis の製品要件、公開 API、実装計画は、それぞれの規範文書と Issue で管理する。
本書に登場する技術、データモデル、段階案は、構想を具体化するための現時点の見通しであり、
実装契約ではない。

## 要旨

研究は、完成した論文や整えられたノートだけから成るものではない。読んだ文献、書きかけのメモ、
実験結果、ソースコード、データセット、注釈、検索語、採用しなかった候補、途中で捨てた仮説など、
異なる成熟度の記録が長い時間をかけて蓄積する。これらは用途ごとに異なるアプリケーションへ保存
され、研究者自身の記憶の中でだけ結び付いていることが多い。

本構想は、そうした分散した研究記録を一つのアプリケーションへ移し替えるのではなく、それぞれの
正本と来歴を維持したまま、共通の探索空間へ接続することを目指す。利用者と AI エージェントは、
アプリケーションの境界を越えて過去の研究活動を検索し、関連する記録を見つけ、根拠を確認し、
議論の成果を新しい研究メモとして再び記録へ戻す。

さらに、日々の利用から「何を探し、何を採用し、何を不適切と判断し、何が実際の研究記録へ
つながったか」を学ぶことで、一般的な検索器ではなく、その人の研究の進め方に適応する探索基盤へ
育てたい。ただし、過去の選択を反復するだけの推薦器にはしない。既知の情報を確実に再発見する
能力と、現在の関心に関連する別の記録へ到達する能力を、透明性と利用者の制御の下で改善する。

## 連環という名前

本構想を**連環**、英字では **Renkan** と呼ぶ。

連環は、複数の輪が互いにつながることを表す。ここでいう輪は、Marginalis、文献管理ツール、
Git repository、実験データ管理等の個別アプリケーションだけを意味しない。研究活動に含まれる
記録、探索、議論、引用、再利用も、それぞれ次の活動へつながる輪である。

この名前には二つの意味を込める。

一つは、分散した研究記録の**つながり**である。連環は、すべての記録を一つの保存先へ集約して
出典を消すのではなく、それぞれのデータソースを独立した輪として保ち、その間を識別子、参照、
意味的な類似性、利用者の判断によって結ぶ。個々の輪が自律しているからこそ、つながりを後から
追加し、組み替え、取り外すことができる。

もう一つは、研究活動の**循環**である。

```text
探す
  → 比較し、議論する
  → 研究メモへ記録する
  → 引用と採否から学ぶ
  → 次の探索を改善する
  → 探す
```

静的な関係だけでなく、利用を通して記録と探索が互いを育てる運動を表したいため、「連関」では
なく「連環」を選ぶ。検索結果を返した時点で処理を閉じず、その結果が研究記録へ戻り、後日の
探索を変えるところまでを一つの系として捉える。

連環は、過去の記録だけを反復する閉じた輪を意味しない。新しいデータソース、新しい文献、新しい
問いを接続するたびに輪が増え、研究の探索空間が外へ広がる連なりを目指す。個人化についても、
既知の選好へ閉じ込めるためではなく、蓄積した文脈を手がかりに、別の記録へ到達しやすくするために
用いる。

Marginalis は連環に置き換えられる製品ではなく、連環を構成する最初の輪である。Marginalis が
研究の考察を AsciiDoc の正本として残し、連環がその記録をほかの研究資料と結び、次の探索へ
循環させる。

> **Marginalis は研究の記録を残す。連環は、分散した研究の記憶をつなぎ、次の探索へ循環させる。**

本構想を短く表す言葉として、次を掲げる。

> **分散した研究の記憶を、次の探索へつなぐ。**

## 研究活動はアプリケーションの境界を越えている

研究者は、研究のすべてを一つのアプリケーションで行わない。文献は文献管理ツールへ、考察は
ノートへ、実装は Git repository へ、実験結果はファイルやデータベースへ、注釈は PDF reader へ
保存される。共同研究や議論の記録は、さらに別のサービスへ置かれるかもしれない。

この分散は必ずしも失敗ではない。それぞれの道具が、それぞれの対象に適した正本を管理している
からである。文献管理ツールは書誌情報と PDF を扱うことに優れ、Git はコードの履歴を扱うことに
優れ、Marginalis は研究メモを AsciiDoc として記録することに集中できる。すべてを一つの巨大な
アプリケーションへ集約すれば、個々の道具が持つ専門性と可搬性を失う。

問題は、道具が分かれていることではない。道具の間に存在する関係が、検索可能な形で残らない
ことである。

ある実験ノートの背景となった文献、ある実装判断の根拠となった考察、以前は採用しなかったが
現在の問題には適合する手法、別のプロジェクトで得た知見などは、研究者の頭の中ではつながって
いても、各アプリケーションの検索窓からは見えない。時間が経つと、その関係を思い出すための
手がかり自体が失われる。

したがって必要なのは、新しい万能の保存先ではなく、異なる保存先をまたいで研究の記憶を
再構成できる探索層である。

## 私たちの立場

本構想は、次の立場を採る。

### データソースはそれぞれ正本であり続ける

探索基盤は、Marginalis、文献管理ツール、Git repository、実験データ管理等を置き換えない。
各データソースが管理する本文、メタデータ、識別子、revision、アクセス制御を尊重し、探索に
必要な表現だけを再構築可能な索引として保持する。

この原則により、探索基盤が停止しても元の研究記録は残る。検索方式や埋め込みモデルを変更しても、
研究記録そのものを移行し直す必要はない。データソースを追加・交換するときも、既存の道具を
捨てることを前提にしない。

### 探索の単位をアプリケーションではなく研究対象に近づける

同じ論文が、文献管理ツールの書誌情報、PDF、読書ノート、実験ノートから参照されることがある。
これらは別々の Resource だが、研究上は同じ対象を異なる角度から表している。

探索基盤は、出典を消して一つへ統合するのではなく、出典ごとの Resource を保ったまま、
DOI、arXiv ID、ISBN、明示的な参照、利用者の確認等によって関係付ける。検索結果を単なる文字列の
一致として返すのではなく、どのデータソースのどの記録が、どの研究対象にどう関係するかを
たどれるようにしたい。

### 人間と AI エージェントが同じ根拠へアクセスする

AI エージェントは、探索基盤を人間に代わって検索するだけでなく、複数の検索結果を比較し、
利用者との議論を進め、研究メモの草案を作成する窓口になり得る。そのとき、エージェントだけが
利用できる不透明な知識層を作るべきではない。

人間向け UI と MCP クライアントは、同じ Resource、出典、識別子、引用可能な位置を参照する。
エージェントの回答は、元データへ戻って確認できる検索結果に基づく。検索ハブは「もっともらしい
回答」を正本にせず、回答を構成するための証拠を提供する。

### 検索後の研究活動までを一つの循環として捉える

検索の成功は、検索結果がクリックされたことだけでは測れない。研究において重要なのは、見つけた
情報が考察を変え、比較や議論を生み、後から再利用できる研究記録へ結び付いたかである。

当面は、AI エージェントとの議論を経て、検索結果を引用した AsciiDoc の研究メモが Marginalis に
作成または追記される流れを重視する。

```text
分散した研究記録
        │
        ▼
横断検索・関連探索
        │
        ▼
利用者と AI エージェントによる検討
        │
        ▼
出典を伴う研究メモの作成・更新
        │
        ├─ 次回以降の検索対象
        └─ 検索改善のためのフィードバック
```

Marginalis はこの循環の最初の書込み先であるが、探索対象の境界ではない。将来は注釈、実験計画、
コード上の判断記録など、別の適切なデータソースへ成果を還流する可能性も残す。

## 再発見と関連探索

当面、実現したい探索能力は二つである。

一つは再発見である。以前に書いたノート、読んだ文献、参照したデータを、正確な題名や保存場所を
覚えていなくても探し直せるようにする。「たしか以前、似た失敗について書いた」「著者名は
忘れたが、この考え方を使った論文を読んだ」といった不完全な記憶から、目的の記録へ戻れることを
目指す。

もう一つは関連探索である。現在開いているノートや文献を起点に、別のデータソースにある関連資料を
探せるようにする。語が一致する資料だけでなく、異なる表現で同じ問題を扱う記録、同じ文献を
参照する実験、過去の別プロジェクトで得た考察などを候補として提示する。

次に探求すべき研究課題を自動提案するフロンティア探索は魅力的だが、現段階では優先しない。
再発見と関連探索が十分に機能し、実際の利用と評価が蓄積してから取り組むべき課題である。

## 個人に適応するとはどういうことか

一般的な検索品質だけでは、個人研究の探索には足りない。同じ語でも研究分野によって意味が異なり、
同じ文献でも現在の課題によって重要性が変わる。頻繁に使う略語、独自のタグ、過去のプロジェクト、
新しい文献を優先したい場面と既知の記録を確実に探したい場面もある。

探索基盤は、日常の利用から次のような信号を得られる。

- 利用者が明示的に「関連する」「関連しない」と判断した。
- 複数の候補から一つを採用した。
- 意味的には近いが、今回の意図とは異なる候補を退けた。
- 検索語を言い換えた後に目的の記録へ到達した。
- 検索結果を AsciiDoc の研究メモで引用した。
- 検索を起点にノートを新規作成または実質的に更新した。
- 後日、そのノートや引用を再び参照した。

これらをすべて同じ強さの正例・負例として扱ってはならない。上位に表示された候補は選択され
やすく、AI エージェントの選択にはエージェント自身とプロンプトの性質が含まれる。引用されなかった
候補も、単に今回使われなかっただけで、無関係とは限らない。

そこで、人間による明示評価、AI エージェントの自律選択、人間が承認したエージェントの選択、
研究メモでの引用、単なる表示を区別して記録する。負例についても、「無関係」「意図が違う」
「古い」「重複」「既知だが関連する」等の理由を区別する。

個人化の最初の対象は、大規模な埋め込みモデルそのものではなく、検索候補を並べ替える軽量な
reranker、個人辞書、検索方式の重みでよい。データが十分に蓄積したときに初めて、明示的な正例と
hard negative を使った埋め込みモデルの調整を検討する。

## 個人化が閉じた世界を作らないために

個人化には危険もある。過去に選んだものだけを高く評価すれば、探索基盤は既知の関心を繰り返し、
異なる方法や新しい分野との出会いを減らす。検索結果がなぜ上位にあるのか分からなければ、
誤学習を利用者が修正できない。

したがって、個人化は利用者が確認し、停止し、巻き戻せるものでなければならない。学習した同義語、
出典の優先度、時期の重み、モデル版を可能な範囲で表示する。新しいモデルは過去の評価セットと
shadow ranking で比較してから有効化し、旧版へ戻せるようにする。

また、再発見と新規性を同じ評価軸へ押し込めない。再発見では確実性を優先し、関連探索では少数の
多様な候補を残せるようにする。将来フロンティア探索へ進む場合も、関連度、新規性、不確実性を
区別して扱う必要がある。

## 個人の研究履歴は個人のものである

検索語、閲覧履歴、採否、研究メモへの引用は、完成した論文以上に研究者の関心や未公開の仮説を
明らかにする可能性がある。このデータは単なる操作ログではなく、研究活動そのものの一部である。

初期利用者は一人を想定し、データと学習は本人の管理下で動かす。検索履歴と学習データには保持、
export、削除の経路を用意する。外部の埋め込み API や学習サービスへ本文・検索語を送る場合は、
暗黙の前提にせず明示的に選択できるようにする。

将来、最大 10 名程度の研究室で共有する可能性はある。しかし、共有 workspace を導入しても、
個人の検索語や否定的評価を本人の選択なく共有学習へ混ぜない。共有索引、共有された Resource、
個人の利用履歴、個人モデルを別の層として扱う。

## 完成形を先に固定しない

本構想には未確定な点が多い。接続したいデータソース、適切な Chunk の粒度、埋め込みモデル、
個人化の効果、AI エージェントが検索結果を利用する方法は、実際に使わなければ判断できない。

そのため、最初からすべてのデータソースを扱う巨大な基盤を作らない。まず一つのデータソースで、
検索、MCP、フィードバック、研究メモへの還流が本当に役立つかを検証する。そこで得た契約と運用を
独立した探索基盤へ抽出し、二つ目のデータソースを接続する。複数データソースをまたいで初めて
得られる価値を確認しながら、対象を広げる。

以下は、その第一歩を実装へ落とすための現時点の技術的な見通しである。

---

## 第一歩: Marginalis のあいまい検索

第一段階では Marginalis のノートだけを対象にする。これは構想の縮小版を完成品として作るため
ではなく、横断探索に必要な基本要素を、管理可能な範囲で一通り動かすためである。

検証したいのは、少なくとも次の問いである。

- AsciiDoc のノートを、どの粒度の Resource と Chunk として索引すれば再発見しやすいか。
- 日本語と英語が混在する研究メモで、語彙検索と意味検索をどう組み合わせるべきか。
- ノートの作成、更新、削除に検索投影を確実に追従させられるか。
- MCP クライアントが、出典と一致箇所を失わずに検索結果を利用できるか。
- 人間の判断、AI エージェントの判断、研究メモでの引用を区別して記録できるか。
- 日常利用から得た少量のデータで、検索順位を安全に改善できるか。

この段階で得た Resource、Chunk、検索結果、feedback、outcome の意味を、将来の共通コネクター
契約の原型とする。

## 最小の検索パイプライン

Marginalis のノート全体を利用者へ提示する Resource とし、見出し、段落、抄録に相当するまとまりを
検索用の Chunk とする。検索は Chunk 単位で候補を見つけるが、結果は Resource 単位にまとめる。
これにより、関連する箇所を示しながら、同じノートの断片が結果一覧を埋めることを避ける。

初期の検索は二系統を想定する。

```text
問い合わせ
   ├─ 語彙検索: 題名、タグ、本文、識別子、表記揺れ
   └─ 意味検索: Chunk の埋め込みとの類似性
             │
             ▼
       候補統合・再順位付け
             │
             ▼
   Resource と安全な一致箇所を返す
```

語彙検索は Elasticsearch を候補とする。日本語と英語の全文検索、題名やタグの重み付け、部分一致、
将来の同義語辞書を担当させる。意味検索は PostgreSQL と pgvector を候補とし、埋め込みモデルは
別途選定する。最初は両者の尺度を直接足し合わせず、順位を統合する Reciprocal Rank Fusion 等の
単純で再現可能な方法から始める。

十分な利用データが得られた後、Elasticsearch の順位、BM25、pgvector の距離、Resource 種別、
時期、明示的な評価、過去の引用実績等を特徴量にした軽量な reranker を追加する。

## 検索カタログと検索投影

長期的には、検索ハブ専用の PostgreSQL を共通カタログとして置き、Elasticsearch を再構築可能な
検索投影として扱う構成を想定する。Marginalis が将来 PostgreSQL を正本にしても、Marginalis の
database または schema、DB role と検索カタログは分離する。

検索カタログには、少なくとも次の種類の情報が必要になる。

- データソースと、そのデータソース内での安定した外部 ID
- Resource の種別、題名、著者、日時、タグ、DOI 等のメタデータ
- Resource の revision と削除状態
- Chunk の本文、位置、分割規則の版
- 使用した埋め込みモデル、次元、前処理の版
- データソースからの同期位置と索引 job の状態
- 検索セッション、提示候補、順位、各検索器のスコア
- 人間と AI エージェントを区別した feedback
- 研究メモの作成・更新・引用等の outcome

PostgreSQL はベクトルだけを置く場所ではない。検索結果を元データへ戻すための識別子、フィルターと
個人化に必要なメタデータ、同期の整合性、学習データを結び付ける中心となる。Elasticsearch にも
検索用のメタデータを複製するが、その投影を正本にはしない。

埋め込みモデルを変更するときは既存ベクトルを上書きせず、モデル ID ごとに並行して保持する。
旧モデルと新モデルを同じ評価セットで比較し、切替後も戻せるようにする。

## Marginalis との同期

Marginalis のノートが作成、更新、削除されたとき、検索結果が最終的に同じ状態へ収束しなければ
ならない。

将来 Marginalis が PostgreSQL を正本にする場合は、ノート更新と同じ transaction で outbox
event を記録し、検索側が revision を確認しながら冪等に処理する方式が候補になる。第一段階で
そこまで分離しない場合も、更新されたノートだけを再投影でき、索引を全件再構築できる境界を
用意する。

検索カタログ、pgvector、Elasticsearch を同時に完全同期することは前提にしない。一時的な遅延を
観測可能にし、古い revision の反映を拒否し、失敗した job を再試行できるようにする。削除や
権限縮小は優先して処理し、結果返却時にも現在の状態を確認する。

## MCP による利用

検索ハブは、Marginalis の MCP とは別の OAuth 保護 MCP server とする構成を想定する。検索ハブは
探索を担当し、Marginalis MCP は研究メモの正本を作成・更新する。

最初に必要な検索操作は複雑でなくてよい。

- 検索語と任意のフィルターから Resource を探す。
- 一つの Resource を起点に関連 Resource を探す。
- 検索結果に対する明示的な正例・負例と理由を記録する。
- 検索が研究メモの作成・更新・引用へつながったことを記録する。

検索結果には、検索セッションを識別する ID、Resource の安定 ID、出典、題名、主要メタデータ、
正規 URL、短い一致箇所を含める。AI エージェントはそれを利用者へ示し、議論の後に Marginalis
MCP で AsciiDoc のノートを作成または更新する。

## AsciiDoc の引用を成果として捉える

AI エージェントが検索結果を提示しただけでは、その結果が有用だったとは限らない。Marginalis の
研究メモに実際に引用された Resource は、より強い利用実績になる。

そのため、AI エージェントはノートの保存後に、検索セッション、Marginalis のノート ID と
revision、実際に引用した Resource ID を検索ハブへ報告する。ノートを更新したという事実と、
個々の検索結果を引用したという事実は分けて扱う。議論が有用でも提示文献を引用しない場合が
あるためである。

明示報告だけに依存せず、Marginalis のノート更新 event を検索ハブが受け取り、保存された
AsciiDoc から次の識別子を検出する経路も用意したい。

- DOI の正規 URL または識別子
- arXiv ID、ISBN 等の外部識別子
- Paperpile 等のデータソースが持つ安定 URL
- 将来定義する探索基盤の Resource URI

検出した識別子を検索カタログと照合し、ノート revision と Resource の利用関係を冪等に記録する。
AI エージェントの明示報告と自動検出が一致すれば、引用された Resource の強い正例として扱える。
不一致は自動的に負例へ変換せず、報告漏れ、識別子解決の失敗、引用形式の違いとして調査できる
状態にする。

更新 event だけでは、どの検索セッションが引用の契機だったかを常に特定できない。検索との因果を
学習に使う場合はエージェントの明示報告を用い、自動検出は引用実績の検証、報告漏れの補完、
長期的な利用実績に使う。

## フィードバックから最初に学ぶこと

第一段階で学習したいのは、巨大な個人モデルではない。

まず、検索結果ごとに全提示候補、提示順位、検索器ごとのスコア、モデル版を記録する。その上で、
人間による明示評価、AI エージェントによる選択、人間が承認した選択、研究メモでの引用を区別する。
表示されたが選択されなかった候補は、そのまま負例にしない。

少量のデータでも、次の改善は試せる。

- 個人が使う略語、表記揺れ、同義語を検索語へ反映する。
- 題名、本文、タグ、時期、語彙検索、意味検索の重みを調整する。
- 問い合わせに応じて、語彙検索と意味検索のどちらから多く候補を取るかを変える。
- 明示的に退けられた類似候補を hard negative として reranker を改善する。
- Marginalis で引用された Resource を、その問い合わせに対する強い正例として扱う。

学習は即時に本番順位へ反映せず、日次または週次の batch とする。固定した検索課題と過去の明示
評価で旧モデルと比較し、shadow ranking を経て有効化する。利用者は個人辞書や重みを確認し、
誤学習を削除し、以前のモデルへ戻せるようにする。

## 第二のデータソースとしての Paperpile

Marginalis だけで基本契約を検証した後、Paperpile を第二のデータソースとして接続する。ここで
初めて、ノートと文献をまたぐ横断探索の価値を確かめられる。

現時点で安定した取込経路の候補は、Paperpile の自動同期 BibTeX である。Paperpile はライブラリ
全体、フォルダー、ラベルを Google Drive、GitHub、またはダウンロード URL の BibTeX へ同期
できる。検索側はこれを定期取得し、DOI、題名、著者、年、雑誌、URL、キーワード等を共通
Resource へ変換する。

Paperpile の JSON エクスポートには、ユーザー編集可能なメタデータ、添付、フォルダー、ラベルが
含まれるため、初回取込や整合性確認にも利用できる。PDF は Google Drive へ同期できるが、書誌
Resource との安定した対応付け、本文抽出、OCR は別の取込機能とする。本構想の中心は PDF parser
そのものではなく、抽出済みのテキストとメタデータを共通の探索空間へ接続することにある。

参考:

- [Automatically sync BibTeX files](https://paperpile.com/h/sync-bibtex-files/)
- [Export your library data](https://paperpile.com/h/export-library-data/)
- [Sync with Google Drive](https://paperpile.com/h/sync-google-drive/)

Paperpile との接続後は、Marginalis のノートから関連文献を探す、文献から過去の読書ノートや
実験ノートを探す、同じ DOI を参照する複数の考察をまとめて見る、といった探索が可能になる。
これが、単一アプリケーション内の検索から横断探索基盤へ移る最初の節目になる。

## その先の広がり

二つのデータソースで横断探索を検証した後は、同じコネクター境界を使って対象を増やす。
候補には、別の文献管理ツール、Git repository、実験記録、データセット、PDF 注釈、調査用の
ブックマーク等がある。

コネクターはデータソース固有の取得、revision、削除、アクセス制御を共通 Resource へ変換する。
検索ハブ側はテキストの分割、埋め込み、Elasticsearch 投影、検索、feedback を共通に扱う。
PDF や OCR のような重い前処理は、抽出済みテキストを渡す交換可能なアダプターとして追加する。

段階のイメージは次のとおりである。

1. Marginalis のノートを対象に、あいまい検索、MCP、feedback、引用検出を動かす。
2. 検索カタログと Retrieval Service を独立させ、Marginalis を最初のコネクターにする。
3. Paperpile を接続し、ノートと文献をまたぐ検索と関連探索を実現する。
4. 個人利用の評価データから軽量な reranker と検索語の個人化を導入する。
5. コード、実験記録、データセット、注釈等へデータソースを広げる。
6. 必要性が確認された場合に、最大 10 名程度の研究室 workspace を追加する。
7. 再発見と関連探索が十分に機能した後、フロンティア探索を再評価する。

## 第一歩の成功をどう判断するか

第一歩の成功は、高度なモデルを導入したかではなく、研究活動の循環が成立したかで判断したい。

- 不完全な記憶から、以前の Marginalis ノートを見つけ直せたか。
- 現在のノートから、意味的に関連する別のノートを発見できたか。
- AI エージェントが出典と一致箇所を保ったまま候補を提示できたか。
- 検索結果を材料に利用者と議論し、研究メモを新規作成または実質的に更新できたか。
- 引用した Resource と不適切だった候補を、次回の検索改善へ利用できたか。
- 索引やモデルを作り直しても、元の研究記録と利用実績を失わずに再現できたか。

候補品質には MRR や NDCG 等を使えるが、最終的に重視するのは、検索が研究メモの作成・更新と
後日の再利用につながったかである。ただし、ノート更新回数だけを最適化すると不要な更新を促す
ため、引用、明示評価、後日の参照と合わせて評価する。

## 開いたままにする問い

この構想は、次の問いにまだ答えていない。

- 独立した探索基盤は Marginalis と同じ repository の別 service か、独立製品か。
- Resource と Chunk の安定 ID、外部 URI、削除後の tombstone をどう設計するか。
- AsciiDoc 内で外部 Resource と検索来歴を、可搬性を損なわずどう表現するか。
- Paperpile の BibTeX entry と Google Drive 上の PDF をどう安定して対応付けるか。
- 日本語と英語を含む研究記録に、どの埋め込みモデルと Chunk 粒度が適するか。
- 少量かつ偏りのある個人 feedback から、どこまで安全に学習できるか。
- 関連性を改善しながら、未知の情報との出会いをどう残すか。
- 検索語、採否、引用履歴をどの期間保持し、どう export・削除するか。
- 研究室利用へ拡張するとき、共有索引と個人モデルをどう分離するか。

これらを早い段階で一つの仕様へ固定することは、本書の目的ではない。Marginalis のあいまい検索を
最初の実験場として、実際の研究活動の中で価値と問題を観察し、次の段階の設計判断へつなげる。
