= 現行要件

[#top]
この文書は、現在のMarginalisが提供する機能と運用上の前提を定めます。各要件の識別子は、設計、
試験、受入の対応を追跡するために固定します。検証先は xref:traceability.adoc#top[要件と検証の対応表]、
実装方法は xref:architecture.adoc#top[アーキテクチャ]、REST APIの入出力は
link:../openapi.json[OpenAPI]を参照してください。

== 想定する運用環境

* *REQ-OPS-001 — ホスト構成*: 単一のNixOSホストで稼働すること。
* *REQ-OPS-002 — 保存先*: SQLiteデータベースを正本とすること。
* *REQ-OPS-003 — 想定規模*: 単一ホストで同時利用者10名程度、約1,000ノートの利用を
想定すること。この値は保証する上限ではなく、運用監視と性能試験の基準として扱うこと。
* *REQ-OPS-004 — 認証基盤*: 標準のOIDC IdPで利用者を認証し、利用可否をID tokenのclaimで
管理すること。参照実装はKanidm 1.10とし、結合試験の対象にすること。
* *REQ-OPS-005 — 保存形式の更新*: SQLite schema 22以降の更新は、通常起動時に暗黙に
実行せず、service停止中の明示的な前進migrationで行うこと。migration前に、秘密状態も含む
SQLite全体の一貫した退避を権限0600で上書きせず確定し、整合性と外部キーを検査すること。
migration履歴の基準22から現行版までを連続した履歴として検査し、非対応版、欠番、未来版は
変更せず拒否すること。必要な変更と履歴更新を一つのtransactionで行い、失敗時は元のschemaと
データを保つこと。schema 22より前のデータは、対応する過去版のarchiveで基準へ移すこと。archiveの
保存契約を更新する場合は、入力を変更せず、全件を再検証した別のarchiveへ変換すること。
失敗結果へ本文、token、secret、identityを含めないこと。
* *REQ-OPS-006 — SQLite診断*: 診断はデータベースへ読み取り専用で接続し、schema版、整合性、
外部キー違反件数を報告すること。未対応schemaの起動拒否後も実際の版を繰り返し報告し、
データベース、WAL、SHMの内容と権限を変更しないこと。SQLを実行できない場合は、schema不一致と
区別できる検査名、失敗分類、SQLite result codeを、ノート本文や秘密情報を含めずに報告すること。
* *REQ-OPS-007 — 構造化ログ*: productionログは安定した``event``で処理を識別し、結果と判定可能な
原因分類をfieldで示すこと。HTTP完了ログはrequest ID、method、queryを除くpath、status、
latencyを含むこと。Cookie、token、認可code、client secret、利用者identity、ノートの識別子と
内容、HTTP headerとbodyを記録しないこと。

== データ管理

* *REQ-DATA-001 — ノート正本*: 利用者が記述した完全なAsciiDoc文書、所有者、時刻、revision、
削除状態をSQLiteへ保存すること。題名とタグはAsciiDoc文書から導出し、独立した更新入力に
しないこと。タグは文書headerで出現順に評価した属性環境の最終値から導出すること。
* *REQ-DATA-002 — 書き出し*: 個別ノートをAsciiDocとして書き出せること。ノート、ACL、
削除状態、文献ライブラリ、文献情報の取込元と対応情報、数式マクロ設定をJSONアーカイブとして
書き出し、検証済みアーカイブを空のデータベースへ復元できる
こと。Webセッション、OIDCログイン試行、MCPクライアントとトークンは対象に含めないこと。
* *REQ-DATA-003 — 文書上限*: AsciiDoc文書はUTF-8で512 KiB以下とし、上限超過を解析前に
拒否すること。
* *REQ-DATA-004 — 変更履歴*: AsciiDoc文書の変更履歴を保存しないこと。
* *REQ-DATA-005 — 参照整合性*: ノート参照をAsciiDoc文書と同じtransactionで更新し、閲覧できない
参照先や参照元の存在と件数を開示しないこと。
* *REQ-DATA-006 — 文献ライブラリ*: 文献情報をCSL-JSONの一項目として保存し、``id``をcitation
keyとして扱うこと。利用者ごとに分離し、本人だけが検索、追加、編集、削除できること。同じ利用者の
citation keyは重複を拒否し、編集と削除には現在のrevisionを要求すること。題名、著者、発行年
などを入力から推測しないこと。保存済みの各項目はJSON objectであり、空でない文字列の``id``と
``type``を持ち、``id``が保存済みのcitation keyと一致すること。復元時にこの条件を満たさないデータは
破損として拒否すること。
* *REQ-DATA-007 — 引用の解決*: 本文の``cite:``が名指すcitation keyを、ノートを作成した利用者の
文献ライブラリで解決すること。閲覧者ごとに表示を変えないこと。引用済みの項目だけを重複なく
参考文献一覧へ並べ、本文の引用と一覧の項目を相互に移動できるようにすること。保存する本文へ
一覧を書き込まないこと。番号で示すスタイルでは、参考文献一覧を番号付きで表示し、本文の引用の
番号と一覧の項番を一致させること。番号を一致させられない場合は、番号のない一覧として表示し、
描画そのものは失敗させないこと。ライブラリに無いcitation keyは保存を拒否せず警告として報告し、
表示ではcitation keyのまま示すこと。文献情報の文字列をAsciiDocの記法として解釈しないこと。
* *REQ-DATA-008 — グラフビュー*: 閲覧できるノートと、それらが引用している文献の関係を1回の
読み取りで返すこと。点は閲覧できるノートと、そのノートが引用している文献だけとし、線は始点と
終点の両方が点として現れる場合だけ返すこと。閲覧できないノートの存在、件数、匿名の点を
返さないこと。認可は取得後ではなくSQLite問い合わせの中で適用すること。題名、本文、タグの
いずれかに語を含むノートだけへ絞り込めること。1件のノートを起点として、そこから辿る線の
本数を指定して範囲を絞れること。本数には上限を設け、範囲外の指定を拒否すること。本文を
応答へ含めないこと。
* *REQ-DATA-009 — 作成経路と人手確認*: ノートを最初に保存した経路を``web``、``rest``、``mcp``、
``unknown``の変更不能な値としてサーバー側で記録すること。現在のrevisionを所有者が明示的に
確認した事実を、確認したrevision、時刻、確認者とともに記録し、後のrevision変更では確認待ちへ
戻すこと。旧形式のノートは移行時には推測せず不明とし、移行後のrevision変更で確認待ちへ移すこと。
MCPから確認済み状態を設定できないこと。通常の
REST・MCP応答には確認者を含めず、作成経路と確認状態で認可済みノートを抽出できること。
* *REQ-DATA-010 — CSL-JSON一括取込*: 利用者本人が指定したCSL-JSON配列を、変更を保存しない
事前確認と、明示的な選択後の適用に分けて文献ライブラリへ取り込めること。取込元と外部項目の
対応、前回取り込んだ内容のhash、反映先revisionを保存し、未変更、外部変更、Marginalis内変更、
双方変更、新規、重複を区別すること。双方変更と重複は利用者が項目ごとに扱いを選ぶまで適用せず、
事前確認後に入力、取込元、対応情報、または所有者の文献ライブラリが変わった場合は全体を競合として
拒否すること。既存項目を更新するときはcitation keyを維持し、入力から消えた項目を削除しないこと。
文献項目、取込元、対応情報を一つのtransactionで更新し、一部だけを保存しないこと。入力は1,000項目、
8 MiB、各文字列と入れ子の深さに上限を設け、元ファイルと外部サービスの認証情報を保存しないこと。

== 利用者と権限

* *REQ-AUTH-001 — 利用条件*: 設定したclaim(既定``groups``)の値が、設定した許可値の一覧
(既定``server-users``)のいずれかに一致する利用者だけが利用できること。許可値の一覧を明示的に
空へ設定した場合だけ、issuerで認証できた利用者を全員許可すること。claimへ``email``を使う場合は
``email_verified``がtrueであることも要求すること。
* *REQ-AUTH-002 — 所有者identity*: ノート所有者をOIDCの``issuer``と``subject``の組で識別し、
作成後に変更できないこと。
* *REQ-AUTH-003 — 直接ACL*: 所有者には管理権限、同じ``issuer``のACL共有先には閲覧または
編集権限を付与し、その他の利用者にはノートの存在を開示しないこと。
* *REQ-AUTH-004 — 権限順序*: 実効アクセス水準を閲覧、編集、管理の順に包含すること。
* *REQ-AUTH-005 — 管理者迂回の禁止*: サーバー全体の管理者権限や、所属グループによって
個別ノートのACLを迂回する経路を設けないこと。
* *REQ-AUTH-006 — 認証snapshot*: 署名検証済みID tokenからグループ情報を読み取り、
セッション中はログイン時のidentityと利用可否を保持すること。
* *REQ-AUTH-007 — Webセッション期限*: Webセッションを最終利用から24時間、ログインから
最長7日で失効させ、期限切れまたは取消済みの情報を定期削除すること。

== 接続方法

* *REQ-API-001 — 共通業務規則*: REST API、Web UI、MCPで同じ所有者、ACL、``revision``の
規則を使用すること。
* *REQ-API-002 — REST版*: REST APIを``/api/v3``だけで提供すること。
* *REQ-API-003 — 条件付き変更*: RESTの変更操作では取得時の``ETag``を``If-Match``へ指定し、
同時更新による上書きを防ぐこと。
* *REQ-API-004 — MCP認可*: Authorization Serverを内蔵し、OAuth 2.1 Authorization Codeと
PKCE S256を使用すること。Protected Resource MetadataとAuthorization Server Metadataを公開し、
Client ID Metadata Documentを優先すること。resource、scope、redirect URI、認可code、不透明access
tokenを検証し、認可応答にはAuthorization Serverを識別する``iss``を含めること。
* *REQ-API-005 — MCP権限範囲*: MCPでは、ノートに読み取り、書き込み、削除、外部検索用同期の
``scope``を定義し、文献情報に読み取り、書き込み、削除の``scope``を定義すること。対象と操作が
一致するscopeだけで各toolを許可すること。``scope``は操作の種類だけを
制限し、操作できるノートや文献情報の範囲を広げないこと。利用者全体とクライアント別のscope上限を
区別し、対応scope、両方の上限、
クライアントの要求、利用者の同意の共通部分だけを発行すること。利用者は自分の上限だけを変更でき、
上限を狭めた場合は新しい上限を超える認可codeとtoken familyを同じtransactionで失効すること。
初回の認証challengeは``notes:read``だけを示し、実行時にscopeが不足した場合は、現在のtokenが持つscopeと
今回の操作に必要なscopeを一つの``WWW-Authenticate`` challengeへまとめること。
``notes:sync``は外部検索用コピーへの継続同期だけを許可し、同意画面でコピーの保存と取消後の
削除責任を説明すること。既存tokenへ新しいscopeを自動追加しないこと。
* *REQ-API-006 — MCP接続解除*: RFC 7009 endpointと、利用者本人の認証を要するREST APIから
認可を取り消せること。対象のaccess tokenとrefresh tokenを同じtoken family単位で直ちに
失効すること。
* *REQ-API-007 — MCP tool契約*: ``list_notes``は可視ノートのID、題名、タグ、更新日時、revision、
作成経路、人手確認状態を返し、作成経路と人手確認状態による完全一致の絞り込みを受け付けること。
``get_note``も同じ更新情報を返すこと。``list_note_templates``は、テンプレート識別タグの付いた
可視ノートの概要だけを返すこと。``get_note_profile``は、本文と参考文献を相互に移動できる
完全なAsciiDoc文書例、文献情報を推測しない注意事項、実効advisory規則と重大度、MCPではwarningを
含む書き込みを拒否する方針を返すこと。``structuredContent``は公開契約型、``text``は同じ結果から
組み立てた人とモデル向けの説明とし、不可視なノートの存在や属性を開示しないこと。
``create_note``と書き込みtoolは警告を含む入力を変更前に拒否し、重大度と位置を保った診断を
``advisories_rejected``と``isError: true``のtool結果として返すこと。診断位置はUTF-8 byte spanに加え、
LSP既定のUTF-16 code unitで数えた1始まりの行・列を返すこと。
``get_note_outline``は本文を返さず、見出しの深さ・題名・原文に明示されたアンカー・1始まりで
両端を含む行範囲（子節を含む階層範囲）と総行数を返すこと。アンカーを推測して生成しないこと。
``get_note_fragment``は指定した行範囲のAsciiDoc原文を要約や変換なしで返し、範囲外の指定を
拒否すること。``apply_note_patch``は単一ファイルのUnified Diffを厳密に適用すること。
``expected_revision``の一致とhunkの完全一致を要求し、位置の再探索を行わず、拒否は機械可読な
codeと対象位置の診断で返すこと。``dry_run``では検証まで行い保存しないこと。適用後の全文には
全文置換と同じ検証を適用すること。patchの上限は公開JSON Schemaと``get_note_profile``で
公開すること。全文の置換は``replace_note_source``だけが行い、``update_note``を提供しないこと。
``sync_notes``はcursorを省略した初期一覧と、それに続く``upsert``・``remove``を一つのcursor系列で
返すこと。cursorはactorに結び付け、期限切れを型で区別し、共有取消後は古いcursorから本文を
取得できないこと。削除を示すtombstoneはノートの物理削除後もcursorの有効期間だけ保持すること。
* *REQ-API-008 — 失敗表現の共通化*: 同じ業務上の失敗に対して、REST APIとMCPが同じ``code``と
同じ``message``を返すこと。失敗表現は入力と成功出力と同じく公開契約として定義し、``docs/openapi.json``と
``docs/mcp-tools.json``へ出力すること。保存内容の破損は一時的な障害と型で区別し、利用者向けの
応答では区別を開示しないこと。
* *REQ-UI-001 — React画面*: 一覧、閲覧、編集、共有設定、削除済みノート、文献ライブラリ、
グラフビュー、数式マクロ設定、MCPのアクセス設定、Webhook設定を一つのReactアプリケーションから
REST APIを利用して提供すること。
編集、グラフビュー、削除済みノートは経路へ入ってはじめて読み込み、他の画面の読み込み量を
増やさないこと。
* *REQ-UI-002 — 応答検査*: Web UIはREST応答を実行時に検査し、解釈できない応答を
利用者向けエラーとして扱うこと。
* *REQ-UI-003 — 一覧の状態*: Web UIの一覧は題名、タグ、更新日時、実効アクセス水準を表示し、
タグ、更新日、ページの状態をURLから再現できること。
* *REQ-UI-004 — 編集状態*: Web UIの編集画面は未保存、保存中、保存成功、保存失敗、競合を
区別して通知し、位置を持つ診断からAsciiDoc文書の該当範囲へ移動できること。プレビュー更新に
失敗した場合は、最後に成功したプレビューを失敗状態と区別して表示すること。保存を拒否しない
AdocWeaveの診断は、重大度、安定したcode、説明、UTF-8バイト範囲とともに成功応答へ含め、
最新の入力に対応する診断だけを表示すること。
* *REQ-UI-005 — 描画結果*: 閲覧画面と編集プレビューは同じ描画境界を使用し、目次、表、引用、
リスト、コード、インライン数式、ブロック数式を判読できること。クライアント側の数式組版に
失敗した場合は利用者へ通知し、横幅を超える表、コード、数式は内容ごとにスクロールできること。
すべてのコードブロックへ1から始まる行番号を表示し、AdocWeaveが開始行を公開した場合はその値を
使用すること。コードと数式の表示情報はAdocWeaveの公開要素と``data-*``属性だけから読むこと。
* *REQ-UI-006 — 長文編集*: Web UIは完全なAsciiDoc文書を文字列のまま編集し、執筆とプレビューを
明示的に切り替えられること。切替時も入力位置、選択範囲、編集履歴を維持すること。
行番号、検索、Tabによる字下げと解除、
``Ctrl\+S``および``Command\+S``による保存を提供し、日本語IMEの変換中は保存とプレビュー更新を
開始しないこと。実行時に生成するCodeMirrorの基礎CSSは、HTMLごとのCSP nonceで許可すること。
* *REQ-UI-007 — 数式マクロ設定*: 利用者が所有するノートへ適用するMathJaxマクロを画面から
一括設定できること。閲覧者や編集者の設定ではなくノート所有者の設定を閲覧とプレビューへ適用し、
マクロ名、置換内容、引数の数、件数、全体の大きさを制限すること。
* *REQ-UI-008 — 文献情報の一括取込画面*: CSL-JSONファイルを選び、取込元の名前、項目ごとの
判定理由、反映内容、競合の選択肢を適用前に確認できること。無効な項目は理由とともに除外すること。
未解決の競合、全項目の除外、または事前確認後の競合がある状態では適用しないこと。操作名と入力欄を
支援技術から識別でき、キーボードだけで事前確認、競合の選択、適用を完了できること。
* *REQ-UI-009 — 執筆中の装飾表示*: 編集画面の入力欄は、AdocWeaveの解析結果から導いたspan注釈
だけを根拠に記法の装飾を表示し、ブラウザー内でAsciiDocを独自に解析しないこと。選択範囲が
交差する記法は記法文字を開示し、離れると折り畳むこと。装飾は無効化でき、無効時は素の原文を
表示すること。装飾の有無は保存される内容へ影響しないこと。span注釈は解析した本文と入力欄の
本文が一致する場合だけ採用し、本文の変更中は既存の装飾を編集へ追従させること。日本語IMEの
変換中は装飾の更新を開始しないこと。

== Webhook通知

* *REQ-HOOK-001 — 購読の管理*: 利用者自身が設定画面とREST APIから、送信先URLと通知する
event種別を選んでWebhookを登録、削除できること。署名付きchallengeへの応答を確認した後だけ
通知を開始すること。署名用secretは登録と再生成の応答だけで開示し、一覧、ログ、失敗応答へ
出力しないこと。
* *REQ-HOOK-002 — 通知内容の最小化*: 通知本文にはevent種別、対象ID、revision、発生時刻、
一意なevent IDと契約版だけを含め、ノート本文、文献情報の内容、利用者の識別子を含めないこと。
通知対象はノートの作成・本文更新・削除・復元と文献項目の作成・更新・削除に限り、共有設定と
人手確認の変更を通知しないこと。
* *REQ-HOOK-003 — 配送保証*: 確定した変更と同じtransactionでeventを記録し、同じ送信先へは
発生順に配送すること。配送はat-least-onceとし、受信側がevent IDで重複を除去できること。
失敗した配送は指数backoff（初期5秒、上限1時間）で最大10回試行し、上限へ達した購読は
理由付きで停止して、利用者が失敗した配送の再試行または破棄で再開できること。配送済みの
記録は7日で削除すること。
* *REQ-HOOK-004 — 送信先の制限*: 送信先は公開networkのHTTPS（port 443）だけを許可し、
登録時と送信直前の両方で特別用途addressを拒否すること。redirectへ従わないこと。例外は
運用者が設定で明示したhostに限ること。
* *REQ-HOOK-005 — 署名*: すべての送信に、送信時刻と本文へのHMAC-SHA256署名をheaderで
付けること。受信側が検証できるように、署名の計算方法と本文の形式を公開契約として
文書化すること。

== ノートの共有

* *REQ-ACL-001 — 共有対象*: 所有者だけが、同じOIDC ``issuer``の個人を正確な``subject``で指定し、
閲覧または編集権限を設定できること。
* *REQ-ACL-002 — 非対応範囲*: 共有先の検索・列挙とグループ共有を提供しないこと。
* *REQ-ACL-003 — 所有者専用操作*: 削除、復元、共有設定の変更を所有者だけに許可すること。
* *REQ-ACL-004 — 概要と詳細*: 一覧は本文を含まない概要と現在の利用者の実効アクセス水準を返し、
詳細、関連ノート、変更操作には同じ実効アクセス水準を適用すること。
* *REQ-ACL-005 — 一貫した閲覧*: 閲覧画面のノート、実効権限、描画HTML、関連概要を、一つの
整合した読み取りスナップショットから返すこと。

== 削除と定期処理

* *REQ-LIFE-001 — ソフトデリート*: 所有者がWeb UIからノートを削除し、所有する削除済みノートを
確認して復元できること。削除したノートを30日間復元可能な状態で保管し、期限後にデータベースから
物理削除すること。削除済み一覧は共有先へ存在、件数、題名、時刻を開示しないこと。

== NixOSでの配備

* *REQ-DEPLOY-001 — NixOSモジュール*: SQLite、OIDCクライアント、MCPの有効化と許可するorigin、
Webhook送信先の例外host、バックアップ先を設定でき、OIDCクライアントシークレットを
systemd credentialで渡すこと。
* *REQ-DEPLOY-002 — 設定の単一宣言*: serviceが読み取る環境変数を``MARGINALIS_``接頭辞で統一し、
変数名、必須条件、未設定の判定を一つの宣言から導くこと。起動処理と``diagnose``が同じ宣言を使い、
同じ入力に対して異なる判断をしないこと。MCPの有効・無効は``MARGINALIS_MCP_ENABLE``で明示すること。

== 対応する保存形式

* *REQ-FORMAT-001 — 現行形式*: SQLiteスキーマ22と、AdocWeave package版0.41.0を記録した
``marginalis-archive-17``だけを通常処理で受理すること。``migrate-archive``と``restore-archive``だけは
直前の公開済み保存契約(ADR 0018)だけを移行の入力として受理し、AdocWeave 0.41.0で全件を再検証する
こと。保存契約はarchive形式、AdocWeave package版、note profile版の組とし、3項目をすべて検査する
こと。直前より古い契約と、その他の旧形式を現行版だけで移行せず、公開済みの過去リリースを使う
段階的な移行経路を利用者向け文書へ記録すること。今後の契約変更には、直前の公開済み保存契約から
新契約への変換を必ず含めること。
* *REQ-FORMAT-002 — 文書としての取り出し*: ノートをAsciiDocファイル、文献情報をCSL-JSONの配列
として``tar.xz``形式の書庫1つへ書き出せること。書庫の中でも所有者だけが読める権限を記録し、
削除済みノートを出力せず、題名から作るファイル名が衝突または書庫の外へ出ないこと。
manifestへ形式名、Marginalisの版、AdocWeave packageの版、ノート受理規則の版を記録し、
作成経路と人手確認記録も保存して、取り込む側が移行の要否を判断できること。
* *REQ-FORMAT-003 — 文書としての取り込み*: 書き出した文書一式を、空のdatabaseへ取り込めること。
manifestが記録する版が現行と違う場合は全ノートを現行規則で再検証し、満たさないノートがある
場合はdatabaseを変更せず位置で示すこと。本文の正をファイル、識別子と日時の正をmanifestとし、
書き出し後に本文、所有者、ACLが変わったノートはrevisionと更新日時を進め、以前の人手確認を
現在の版へ引き継がないこと。変更検出値は署名や改ざん防止ではなく、外部編集の判定にだけ使うこと。
manifestに無いファイルを取り込まないこと。書庫の外を指すpathと通常ファイル以外の項目を拒否し、
展開後の大きさに上限を設けること。

一貫して満たすべき設計条件は xref:architecture.adoc#top[アーキテクチャ]を参照してください。v0.3.0時点の
要件と設計判断は``v0.36.0``タグ上の``docs/v0.3.0-design.adoc``に保存しています。
