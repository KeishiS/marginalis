= MCP Authorization Serverの保守

[#top]
この文書は、Marginalisが取り込む共有Authorization Server crateの版を更新する開発者に向けて、Marginalis側の
手順だけを説明します。crate自身の設計、対応仕様、安全上の不変条件、上流での更新手順は、専用リポジトリ
https://github.com/KeishiS/mcp-authorization-server[KeishiS/mcp-authorization-server]の``docs/architecture.adoc``と
``docs/maintenance.adoc``を正本とします。ここでは同じ内容を繰り返しません。

Marginalisへの接続方法と利用者が確認できる動作は xref:../user-guide/mcp.adoc#top[MCPへの接続と認可]、中核を製品から
分けた理由は xref:adr/0008-mcp-authorization-serverの中核を製品から分離する.adoc#top[ADR 0008]、独立リポジトリ
へ移した理由は xref:adr/0012-共有authorization-serverを独立リポジトリで配布する.adoc#top[ADR 0012]を参照して
ください。

== 取り込み方

``mcp-authorization-server``と``mcp-authorization-server-cimd``は、Marginalisのworkspaceには含めません。
ルート``Cargo.toml``の``[workspace.dependencies]``で、版と40桁の完全なcommit SHAを一度だけ宣言します。
各crateはそれを``workspace = true``で参照します。branch名やtag名は依存指定に使いません。tagは付け替え
られるため、同じ指定が別の内容を指す可能性があるからです。

``testkit`` featureはdev-dependencyだけで有効にします。契約試験の補助コードを製品バイナリーへ含めない
ためです。

Nixでは``flake.nix``の``cargoLock.outputHashes``へ、2 crate分の取得ハッシュを追加します。revisionの正本は
``Cargo.lock``であり、flake inputは追加しません。

== Marginalisに残る責務

上流リポジトリが検証する範囲と、Marginalisが検証する範囲は次のように分かれます。

[cols="1,1",options="header"]
|===
|検証対象
|検証するリポジトリ

|中核へのHTTP・database・製品依存の混入
|``mcp-authorization-server``

|CIMDから中核への依存方向
|``mcp-authorization-server``

|CIMDのSSRF対策と資源制限
|``mcp-authorization-server``

|Marginalis内部の層と依存方向
|Marginalis

|SQLite adapterのrepository契約
|Marginalis

|固定した版・URL・SHA・Nixのハッシュ
|Marginalis

|OAuthのHTTP endpointとMCP統合
|Marginalis
|===

Marginalisが所有し続けるのは、Kanidmで確認した主体の受け渡し、Web session、Cookie、CSRF、同意画面、
``notes:*``と``bibliography:*``の意味、HTTP endpoint、SQLite schemaとtransaction、token hashの保存、
利用者とclient別のscope上限、MCP toolとscopeの対応です。

SQLite schemaとarchive形式はMarginalis側の契約です。上流crateを整理したことだけを理由に変更せず、
変更が必要な場合は通常のdatabase・archive移行手順を別に設計します。

== 新しい通常Releaseの確認

上流リポジトリはMarginalisと同じ開発者が保守するため、新しいRelease の公開はその作業の中で分かります。
定期的に照合するworkflowは置かず、更新を取り込むときに上流の最新Releaseを直接確認します。

[source,sh]
----
gh release view --repo KeishiS/mcp-authorization-server --json tagName,isDraft,isPrerelease
----

draftとprereleaseは取り込みの対象にしません。取り込みを保留する場合は、理由と再確認時期をIssueへ
記録します。

== 固定revisionの更新手順

[arabic]
. 上流リポジトリで公開されたtagから、対象commitの40桁の完全なSHAを確認します。tag名ではなくSHAを
使います。注釈付きタグでは``refs/tags/<tag>``が指すのはタグobjectであり、commitではないため、
次の2段階でタグobjectを解決して最終的なcommitのSHAを取得します。
+
[source,sh]
----
gh api repos/KeishiS/mcp-authorization-server/git/ref/tags/<tag> --jq '.object.sha' |
  xargs -I{} gh api repos/KeishiS/mcp-authorization-server/git/tags/{} --jq '.object.sha'
----
. ルート``Cargo.toml``の2 crateの``version``と``rev``を、同じ値へ同時に更新します。
. ``cargo check --workspace``を実行して``Cargo.lock``を更新します。
. ``flake.nix``の``cargoLock.outputHashes``のkeyとハッシュを更新します。keyは``<crate名>-<版>``です。
正しいハッシュは``nix build .#default``の失敗メッセージが示します。
. ``cargo make pinned-git-crates``を実行し、版、URL、revision、到達性、ライセンス、
``testkit``の混入、Nixのハッシュを確認します。
. ``cargo make verify``と``cargo make pre-push``を実行します。
. 上流の公開APIが変わった場合は、Marginalis側の呼び出しとSQLite adapterを同じPull Requestで更新します。
. 外部から見える動作が変わる場合は xref:protocol-regression.adoc#top[MCPプロトコル回帰試験] と公開文書を
更新します。
. ChatGPT、Claude Code、Codex CLIで接続から取消・再認可までを確認します。
. 利用者や運用者へ影響する変更だけを、公開する版のGitHub Release Notesへ記載します。

== セキュリティー修正の反映

上流の脆弱性は上流の非公開advisoryで管理し、修正版を先に公開します。Marginalisは、公開された修正commitの
SHAへ固定revisionを更新し、上記の手順で統合を検証します。

利用側の更新が終わるまで、脆弱な入力例、token、client ID、内部URLなどを公開のIssue、Pull Request、
ログ、試験成果物へ出しません。報告と公開の時期は xref:security.adoc#問題の報告[セキュリティー方針]に
従います。
