= Webhook署名secretを平文で保存する

[#top]
* 状態: 採用
* 日付: 2026-08-13
* 関連Issue: \#431、\#450

== 背景

Webhook配送では、送信本文と時刻をHMAC-SHA256で署名し、受信側が送信元を検証できるようにします。
署名の計算には共有secretの平文が必要です。

Marginalisの既存の秘密情報(Webセッション、MCPのaccess token、同期cursor)は、SQLiteへ
SHA-256 hashだけを保存し、平文を保持しません。この方式は「提示された値と保存値の一致確認」には
使えますが、サーバー側が値そのものを使う署名計算には使えません。

== 決定

Webhook署名secretは、SQLiteの``webhook_subscriptions``表へ平文で保存します。あわせて次を守ります。

* secretの平文は、subscriptionの作成応答と明示的な再生成の応答でだけ返します。通常の取得応答、
HTML、構造化ログ、エラーには出力しません。
* ``webhook_subscriptions``、``webhook_outbox_events``、``webhook_deliveries``はarchiveへ
含めません。復元した環境が自動でWebhook配信を始めることはなく、送信先とsecretは復元後に
登録し直します。

== 理由

* Marginalisは単一ホストで動作し(REQ-OPS-001)、SQLiteデータベースファイル自体がOSの
ファイル権限で保護された信頼境界の内側にあります。データベースを読める攻撃者は、secretの
有無にかかわらずノート本文を含む全データへ到達できるため、secretだけを暗号化しても
守れる範囲がほとんど増えません。
* サーバー鍵による暗号化(envelope encryption)は、鍵の配布・交換・紛失時の再登録手順を
運用へ追加します。個人開発の運用規模に対して、得られる防御に見合いません。
* hash保存では署名を計算できないため、この用途には選べません。

== 影響

* データベースファイルの読み取り権限の管理が、これまでどおり秘密情報保護の前提です。
バックアップの保護要件も同じです(xref:../../user-guide/nixos.adoc#top[NixOSでの運用])。
* 受信側でsecretが漏えいした疑いがある場合は、設定画面からの再生成で新しいsecretへ
切り替えます。
