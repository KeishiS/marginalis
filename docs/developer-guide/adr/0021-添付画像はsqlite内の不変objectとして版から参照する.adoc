= 添付画像はSQLite内の不変objectとして版から参照する

[#top]
* 状態: 採用。Issue \#540で実装
* 日付: 2026-08-20
* 関連Issue: \#540、\#541
* 関連ADR: xref:0002-sqliteを正本として維持する.adoc#top[ADR 0002]、
xref:0018-archiveは直前の公開済み保存契約からだけ移行する.adoc#top[ADR 0018]、
xref:0020-ノートの版履歴は完全な状態を追記して保存する.adoc#top[ADR 0020]

== 背景

MarginalisのノートはAsciiDoc原文だけを正本としており、画像を保存する経路がありません。外部URLの画像を
許可すると、閲覧した時点で外部へ接続し、相手側の変更や停止によって表示が変わります。また、ノートのACL、
archive、30日間の削除保持と画像の生存期間を別々に管理すると、本文だけを復元できても当時の図を表示できない
状態になります。

添付には、現在の本文へ追加する前のuploadと、過去版だけが参照する状態があります。現在版から参照が消えた
時点でbytesを削除すると、版履歴の表示と復元が壊れます。一方、参照されないuploadを無期限に保存すると、
失敗した編集操作だけでdatabase容量を消費します。

== 用語

この決定でいう *添付object* は、利用者がuploadした一つの画像について、識別子、元のファイル名、
サーバーが内容から判定したMIME type、バイト数、SHA-256、bytesをまとめた変更不可の記録です。
*版の参照集合* は、``(note_id, revision)``が表示に使う添付objectの識別子を重複なしで並べた集合です。

== 決定

=== 保存と上限

*添付objectをSQLiteのBLOBとして保存します*。metadata、bytes、ノートとの所属、版の参照集合を同じdatabaseの
外部キーとtransactionで扱います。``dataDir``配下の別ファイルやobject storageとの二段階更新は行いません。
想定する単一NixOSホスト、約1,000ノートの構成では、障害時の整合回復とbackup漏れを防ぐ単純さを優先します。

初期版ではPNG、JPEG、WebPだけを受理します。申告された``Content-Type``や拡張子ではなく、bytesのsignatureで
形式を決めます。SVG、HTML、音声、動画、外部URLからの取得は拒否します。SVGは画像として配信してもscript、
外部参照、XML処理を含み得るため、無害化処理を持たない初期版では受理しません。

上限の正本を``ATTACHMENT_POLICY``へ置き、次を同時に検査します。

* 1件8 MiB
* 一つのノートが保持する32件
* 一つのノートが保持する合計64 MiB
* 元のファイル名200文字

過去版だけが参照するobjectも件数と合計容量へ含めます。上限を超える場合は一部だけ保存せず、upload全体を
拒否します。大容量の一般ファイル保存は対象外です。

=== 本文記法と版

本文では``image::attachment:<attachment_id>[]``だけを内部画像として受理します。``attachment_id``はUUIDv7で、
画像は同じ``note_id``に属していなければなりません。ブラウザーはこの記法を解析せず、AdocWeaveが返す
resource queryをサーバーが解決します。描画時にはACLを検査する
``/api/v3/notes/<note_id>/attachments/<attachment_id>/content``、保存済みMIME type、バイト数を
AdocWeaveへ渡します。配備先のサブパスはHTTP adapterが加えます。ノート閲覧画面の``/notes/<note_id>``と
添付画像のREST APIを同じ接頭辞として扱いません。

本文を保存するtransactionで、解析結果の添付IDがすべて同じノートに存在することを再確認し、新しいrevisionの
参照集合として保存します。ACL変更、人手確認、削除、削除からの復元は、直前の参照集合を新しいrevisionへ
コピーします。過去版の復元は、その版の原文と参照集合を現在の検査規則へ通し、新しいrevisionへ保存します。

uploadは編集途中のobjectを先に保存し、本文を保存した時点でrevisionから参照します。参照を持たないobjectだけを
明示的に削除できます。現在版または履歴のどれかが参照するobjectは削除を拒否します。どの版からも参照されない
uploadは、作成から30日の保持期間を過ぎた場合に日次保守処理で削除します。保守処理と本文の保存が同時になっても、
SQLiteのtransactionにより、先に参照が確定したobjectは保持し、先に期限切れ削除が確定したobjectへの保存は
全体を失敗させます。ノートを30日後に物理削除すると、全履歴と添付objectを外部キーのcascadeで一括して
削除します。

=== 認可と配信

一覧とbytes取得は必ず``note_id``と``attachment_id``の組で受け、現在のノートACLをSQLite内で検査します。
単独の添付IDやSHA-256を公開取得経路にしません。uploadと未参照objectの削除には編集権限を要求します。
削除済みノートでは、履歴と同じく所有者だけが取得できます。

応答の``Content-Type``は保存済みの判定結果だけを使い、``X-Content-Type-Options: nosniff``、
``Content-Disposition: inline``、private cacheを付けます。元のファイル名をHTTP pathへ使いません。

=== archiveと文書書庫

archive 18はまだ公開していないため形式番号を増やさず、全添付objectと全revisionの参照集合を必須項目として
追加します。bytesはbase64で表し、取り込み時に形式、長さ、SHA-256、所属、参照先、上限を再検査します。
直前の公開済み契約であるarchive 17には添付がないため、空集合として移行します。

``export-documents``は現在版が参照する画像をノートごとの``attachments/``へ書き出し、manifestへ
``attachment_id``、相対path、MIME type、バイト数、SHA-256を記録します。過去版だけが参照する画像は、現在状態を
他の道具へ渡す目的と異なるため含めません。完全な復旧には全履歴を持つarchiveを使います。

=== MCP

初期版ではMCP toolへbytesのbase64を載せません。大きな応答、tool結果の複製、モデルcontextへの不要な混入を
避けるためです。MCPから本文を編集するときも添付IDの存在検査は同じように行います。agentが添付を取得する
実需要が生じた場合は、認証済みHTTP URLまたはMCP Resourceを別の公開契約として検討します。

== 帰結

ノート、履歴、添付、archiveを一つのSQLite transactionと参照整合性で扱えるため、別保存先の孤児修復や
backup順序を持ちません。添付を変更不可にすることで、同じrevisionの表示内容が後から差し替わりません。

一方、SQLite databaseとJSON archiveは画像のbytes分だけ大きくなり、base64を使うarchiveは元のbytesより大きく
なります。上限と実際のbackup時間を運用で測定し、SQLiteが保守上の支配要因になった場合だけ保存adapterを
再検討します。

== 代替案

=== ``dataDir``配下のファイル

大きなbytesをSQLiteから分離できますが、metadata transactionとfileのrename、削除、backupの間に二段階の
整合処理が必要です。現行規模では保守する故障状態が増えるため採用しません。

=== 内容hashを公開識別子にした全ノート共通の重複排除

同じ画像の保存量を減らせますが、存在確認や応答時間から他のノートの内容を推測させない設計が必要です。
一つのノート内の上限で容量を制御できる初期版では、ノートに属する不透明なIDを優先します。

=== 現在版だけの参照を保存

表は少なくなりますが、本文を過去版へ復元したときに画像を再現できません。版履歴を完全な状態として扱う
ADR 0020と矛盾するため採用しません。

== 再検討条件

* 代表的な運用データで、添付BLOBがSQLiteのbackup時間または復旧時間の支配的な要因になった場合
* 8 MiBを超える研究データ、動画、または一般ファイルの保存が継続的に必要になった場合
* SVGを受理するための無害化処理と、出力CSPを含む公開契約を一つに定められる場合
* MCP clientから添付bytesを直接取得する具体的な利用者と上限要件が現れた場合
