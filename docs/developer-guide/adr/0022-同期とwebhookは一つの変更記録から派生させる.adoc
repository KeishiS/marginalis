= 同期とWebhookは一つの変更記録から派生させる

== 背景

検索用投影への増分同期とWebhookは、どちらもノートや文献情報の確定した変更を外部へ伝えます。
従来は、同期用の変更索引とWebhook用の``webhook_outbox_events``へ、別々のtriggerが
同じ変更を記録していました。この構造では、新しい変更操作を追加するときに二系統のtriggerを更新する
必要があります。一方だけを更新してもデータの保存自体は成功するため、記録漏れを型検査や外部キーで
検出できません。

同期とWebhookでは、必要な対象と保持期間が異なります。同期はACLで共有された利用者ごとに最新状態を
35日間保持し、Webhookは所有者が登録した送信先ごとに配送状態を保持します。両者を同じ公開契約へ
統合するのではなく、変更の発生だけを一度記録し、それぞれに必要な状態を派生させる必要があります。

== 決定

=== 共通の変更記録

SQLiteの``domain_changes``を、同期とWebhookが共有する変更記録とします。ノート、ACL、文献項目を
変更するtriggerは、この表だけへ一件の変更を追記します。変更記録には連番、再送時にも変わらない
``event_id``、所有者、変更種別、対象ID、revision、発生時刻を保存し、本文、CSL-JSON、外部identityは
保存しません。ACLの付与と取消だけは、同期対象を特定する``affected_principal_id``も保存します。

変更種別のうち、``note.created``、``note.updated``、``note.deleted``、``note.restored``と文献項目の
作成・更新・削除はWebhookへ公開します。ACL変更と人手確認などの``note.state_changed``は同期だけに
使い、Webhookへ配送しません。これにより、Webhookの公開契約は変えずに、確定した変更を記録する入口を
一つにします。

``domain_changes``は監査履歴ではありません。ノートの版履歴は引き続き``note_revisions``を正本とし、
変更理由と当時の完全な状態を保持します。共通変更記録は、外部の利用先を現在状態へ収束させるための
一時的な記録です。

=== 用途別の派生状態

検索用同期では、``domain_changes``の連番を参照する``note_sync_projection``を、利用者とノートの組ごとの
最新状態として保持します。ノート自体の変更はその時点で閲覧できる全利用者へ、ACL変更は対象利用者へ
だけ反映します。本文は同期時に現在のノートと認可へ結合するため、共有取消後に保存済みの変更記録から
本文を取得できません。

Webhookでは、有効な購読に対する``webhook_deliveries``だけを共通変更記録から作ります。配送処理は
``domain_changes``の連番と公開対象の変更種別を読み、従来と同じ``event_id``、署名、順序、再試行規則を
使います。同期用の内部変更種別から配送行は作りません。

=== 保持と復元

配送済みまたは破棄済みの配送状態は7日後に削除し、同期の最新状態は35日後に削除します。
``domain_changes``の行は、同期状態と未配送Webhookのどちらからも参照されなくなった場合だけ削除します。
一方の短い保持期間によって、もう一方が必要とする記録を失わないためです。

共通変更記録、同期状態、cursor、Webhook購読、配送状態は運用中の一時状態であり、archiveへ含めません。
archiveを復元すると、外部検索用投影は全量同期から、Webhookは新しく登録した購読と復元後の変更から
再開します。

=== schema 22からの移行

schema 22のWebhook eventは、``event_id``、連番、配送状態を維持して``domain_changes``へ移します。
未配送の外部通知を失わず、移行後の再送でも同じeventとして扱うためです。

schema 22の同期cursorと変更索引は移行しません。同期用とWebhook用で別々だった連番を一つへ統合すると、
既存cursorの位置を同じ意味の連番へ写せないためです。移行後は古いcursorを未知として拒否し、外部検索用
投影に全量同期を要求します。本文の正本はSQLiteに残るため、データを失わず再構築できます。

== 帰結

新しいノート操作や文献操作を追加するときは、共通変更記録への反映を一度決めれば、同期とWebhookの
派生処理が同じ連番を参照します。保存に成功したのに片方の外部連携だけが変更を認識しない状態を
減らせます。また、同期の最新状態とWebhook配送の責務、保持期間、公開契約は分離したまま維持できます。

一方、Webhookの連番には同期専用の変更による欠番が現れます。連番は順序を示す値であり、連続性を
公開契約としていないため許容します。``domain_changes``は二つの用途の参照がなくなるまで残るため、
配送済みWebhookだけを基準にした場合より長く保持されることがあります。

== 代替案

=== 二つの変更表を維持する

既存コードの変更は少なく済みますが、変更種別を追加するたびに二系統の記録処理と試験を保守します。
個人開発で見落としを防ぐ負担が継続するため採用しません。

=== applicationから同期とWebhookへ明示的に二回記録する

操作ごとの意図はRustコードに現れますが、一括取込を含むすべての保存経路で二つの呼出しを同じ
transactionへ入れる必要があります。呼出し忘れをデータベース制約で防げず、共通記録も得られないため
採用しません。

=== 完全なevent sourcing

変更記録から現在のノートや文献情報を再構築すれば正本を一つにできますが、現在状態の読み取り、認可、
archive復元、schema migrationが複雑になります。本件に必要なのは外部連携用の一時的な変更通知であり、
正本の置換ではないため採用しません。

== 再検討条件

* 変更記録を法的または運用上の監査履歴として長期保存する要件の成立
* SQLite triggerでは表現できない外部連携対象の増加
* 代表負荷で、共通連番または派生triggerが書き込み性能の支配要因になることの確認
