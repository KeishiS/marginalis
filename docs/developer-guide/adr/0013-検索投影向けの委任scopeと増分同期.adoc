= 検索投影向けの委任scopeと増分同期

[#top]
* 状態: 採用
* 日付: 2026-08-08
* 関連Issue: \#405、\#406

== 背景

連環（Renkan）は、Marginalisで閲覧できるノートを外部の検索用投影へ複製します。従来は
``notes:read``で``list_notes``と``get_note``を繰り返し、一覧から消えたノートを削除として扱って
いました。この方式では、変更のない本文も毎回取得し、削除、共有取消、保持期間後の物理削除を
区別できません。また、通常の閲覧許可だけでは、本文を別の保存先へ継続的に複製することが
同意画面から分かりません。

== 決定

*専用scope*: ``notes:sync``を追加し、MCPの``sync_notes``だけを許可します。``notes:read``は
従来の一覧・本文取得だけを許可します。同意画面では、外部に検索用コピーを継続保存することと、
認可を取り消してもMarginalisから保存済みコピーを削除できないことを明示します。既存tokenや
明示済みのscope上限へ``notes:sync``を自動追加しません。

*初期一覧と変更の一つのcursor*: cursorを省略した呼出しは、その時点の変更番号を境界として
可視ノートをID順に返します。初期一覧の終了後は、同じcursor系列で境界より後の``upsert``と
``remove``を返します。``remove``の理由は``deleted``または``access_revoked``です。cursorは
actorに結び付けた推測困難な値とし、SQLiteにはSHA-256 hashだけを保存します。有効期間は35日です。
期限切れは、改ざんや別actorでの利用と区別した公開エラーで返します。

*本文を持たない変更索引*: SQLiteの共通変更記録にはノートID、変更種別、連番、時刻を保存し、
同期用の索引にはactorとノートの組ごとの最新状態だけを派生させます。``upsert``の本文は同期時に
現在のノートとアクセス権へ結合します。共有取消後に古いcursorを使っても、索引に残った本文を
返せない構造にするためです。同じactorとノートの古い状態は新しい状態で置き換え、監査履歴にはしません。

ノート作成、更新、共有変更、削除、復元と変更索引はSQLiteの同じtransactionで更新します。削除の
tombstoneはノート正本を物理削除した後も35日間保持します。cursorと変更索引は日次の
``purge-expired``で削除します。
Webhookと共有する変更記録、用途別の派生状態、保持期間の関係は
xref:0022-同期とwebhookは一つの変更記録から派生させる.adoc#top[ADR 0022]で定めます。

*archiveからの分離*: 同期cursor、変更索引、OAuth状態は業務データのarchiveへ含めません。archiveを
空のdatabaseへ復元した後、外部投影はcursorを省略した全量同期から再開します。

== 結果

連環は約1,000件のノートをページ単位で初期化し、以後は変更分だけを取得できます。初期一覧の開始後に
生じた更新は、一覧終了後の変更段階で取得するため欠落しません。同じcursorの再試行は同じ位置から
収束できますが、共有取消を直ちに反映するため、応答のbyte単位の一致は保証しません。

外部投影は``remove``とcursor更新を同じtransactionで適用します。cursorが期限切れの場合は、別領域へ
全量を組み立ててから現行投影と入れ替えます。これにより、途中まで作った投影を検索へ公開しません。

== 代替案

*``notes:read``を再利用する*: scope数は増えませんが、通常閲覧と外部への継続複製を同意画面で区別
できないため採用しません。

*更新日時による差分取得*: 同じ時刻の更新、時計のずれ、共有取消を安全に表せないため採用しません。

*本文を含む変更履歴*: 読み取りは単純になりますが、共有取消後も過去の本文が保存層へ残ります。
必要なのは監査ではなく検索投影の収束なので採用しません。

*署名付きの自己完結cursor*: server側の保存を減らせますが、古いcursorが保持する位置を失効させにくく、
actor境界と保持期間の検査も複雑になるため採用しません。

== 再検討条件

* 35日を超えて停止する検索投影を、全量同期なしで復旧する必要が生じた場合
* 変更履歴を監査記録として保存する別要件が生じた場合
* ノート数または共有先数が、actor別の小さな変更索引では処理できない規模になった場合
* REST APIからも同じ同期契約を提供する利用側が現れた場合
