= archiveは直前の公開済み保存契約からだけ移行する

[#top]
* 状態: 採用
* 日付: 2026-08-20
* 関連Issue: \#544
* 置換対象: xref:0017-archiveの取り込み互換は直近5マイナー世代に限定する.adoc#top[ADR 0017]

== 背景

ADR 0017は、``migrate-archive``と``restore-archive``が直接受理する旧archiveを、直近5マイナー
世代のリリースが書き出した契約へ限定しました。この判断により、すべての旧契約を現行コードで
保守する状態は解消しました。

一方、Marginalisでは保存契約を変更しない機能追加でもマイナー版を上げます。そのため、5世代が表す
期間はリリース頻度に左右されます。同じ保存契約のままリリースが続くと、保存データの構造が変わって
いないにもかかわらず旧契約が受理対象から外れます。利用者が復元できる期間と、実装が保守する変換の
境界をマイナー版では正確に表せません。

ここでいう保存契約は、archiveの``format``、``adocweave_package_version``、
``note_profile_version``の組です。この3項目がすべて同じarchiveを同じ契約として扱います。
直前の公開済み保存契約とは、現行契約と異なる契約を最後に書き出したGitHub Releaseの契約を指します。
開発途中のcommitや、公開物が作られなかったタグだけの契約は数えません。

== 決定

*``migrate-archive``と``restore-archive``が変換する旧契約を、直前の公開済み保存契約1件だけに
限定します*。実装では複数件の一覧を持たず、``PREVIOUS_MIGRATION_CONTRACT``が形式、AdocWeave
package版、note profile版を一組だけ保持します。現行契約は従来どおり変換せず受理します。

*保存契約が変わらないリリースでは受理範囲を変更しません*。マイナー版またはpatch版を上げても、
3項目の組が同じなら``PREVIOUS_MIGRATION_CONTRACT``を変更しません。保存契約を変更するリリースでは、
変更前に最後に公開した契約を直前契約として設定します。

*それより古いarchiveは公開済みリリースで段階的に変換します*。ADR 0018の採用後に保存契約を変更する
リリースは、直前の公開済み保存契約から新契約への変換を必ず含めます。利用者は入力契約を受理する
過去のリリースを一時的な環境で実行し、その出力を次のリリースへ渡します。各変換は入力を変更せず、
変換先の契約を名乗る別のarchiveを出力します。古い実行環境は通常運用の秘密情報やネットワークへ接続せず、
移行対象のarchiveと出力先だけを渡して使用します。

ADR 0018より前の公開版には、隣接する公開契約を受理しなかった版があります。既存の旧契約には、
複数の旧契約を受理できる最後のv0.45.0を集約経路として使い、その出力を現行版へ渡します。

*契約とリリースの対応は利用者向け文書を正とします*。
xref:../../user-guide/nixos.adoc#保存契約の履歴[保存契約の履歴]へ、契約の3項目、書き出した版、
現行へ持ち上げるために使う公開済みリリースと出力契約を記録します。保存契約を変更するリリースでは、
コード、変換試験、対応表、移行例を同じ変更で更新します。

この判断はarchiveの論理契約だけを対象とします。SQLite schemaを前進専用のmigrationで更新する場合は、
現行バイナリが必要なmigrationを順番に適用します。SQLite schemaの更新に過去のサーバー版を要求する
判断ではありません。

== 帰結

現行コードが持つ旧契約の型、変換分岐、試験は常に1契約分になります。保存形式を変えないリリースが
互換期間を消費しなくなり、実装上の境界と利用者が見る契約履歴が一致します。

2契約以上古いarchiveの復元には過去リリースが必要です。必要な版と手順は対応表から判断できますが、
一時環境の準備は利用者の負担になります。公開済みリリースとタグを削除せず、今後の契約変更ごとに
隣接変換を検証することで、段階的な到達経路を維持します。

== 代替案

=== 直近5マイナー世代を維持

一度に取り込める範囲は広くなりますが、保存契約と無関係なリリース頻度で範囲が変わります。複数の
旧契約を現行コードで保守する必要も残るため、採用しません。

=== 一定期間に公開された契約を受理

利用者が見る期間は明確になりますが、期限内に複数の契約変更があれば現行コードの保守件数が増えます。
個人開発で保守する上限を構造的に1件へ固定できないため、採用しません。

=== すべての旧契約を現行版で変換

利用者の操作は最も少なくなりますが、旧契約ごとの型、補完、再検証、試験を削除できません。過去の
実装判断が現行設計の変更を妨げるため、採用しません。
