= ノートの版履歴は完全な状態を追記して保存する

[#top]
* 状態: 採用。Issue \#541で実装
* 日付: 2026-08-20
* 関連Issue: \#541、\#540
* 関連ADR: xref:0002-sqliteを正本として維持する.adoc#top[ADR 0002]、
xref:0018-archiveは直前の公開済み保存契約からだけ移行する.adoc#top[ADR 0018]、
xref:0019-利用者の認可は内部principalに結び付けsqliteを前進移行する.adoc#top[ADR 0019]

== 背景

従来の``revision``は同時更新による上書きを防ぐ番号であり、SQLiteには最新のノートだけを保存して
いました。以前の本文を調べるには、日次archiveを別のdatabaseへ復元して対象時点を探す必要が
あります。通常の編集、共有設定、人手確認、削除と復元のどの操作で版が進んだかも、ノート単独では
確認できません。

版履歴と添付ファイルには共通の保存期間があります。過去の本文が添付を参照する場合、現在の本文から
参照が消えただけで添付を削除すると履歴を再現できません。そのため、添付を追加する前に、各版を
識別し、削除済みノートの保持期間とarchiveで失わない履歴の境界を定める必要があります。

== 用語

この決定でいう *完全な状態* は、ある``revision``が確定した直後の題名、AsciiDoc原文、タグ、削除状態、
人手確認状態を一件で復元できる記録です。差分だけを前の版へつないだ記録ではありません。
所有者、作成日時、作成経路はノートの生存期間中に変わらないため、履歴行からノート本体を参照します。
ACLは過去の共有先を保存せず、現在のACLを履歴の閲覧判断に使います。

== 決定

=== 追記だけを行う完全な状態

*revisionが変わる操作では、変更後の完全な状態を同じSQLite transactionで``note_revisions``へ一件
追記します*。対象は作成、本文更新、ACL更新、人手確認、ソフトデリート、削除からの復元、過去版の
復元です。履歴行は更新しません。ノートを30日後に物理削除するときだけ、外部キーのcascadeで履歴も
削除します。

各履歴は``(note_id, revision)``で一意にし、変更時刻、変更者の``PrincipalId``、変更種別を持ちます。
変更者を外部identityではなく``PrincipalId``へ結び付けるため、OIDC issuerを引き継いでも同じ利用者の
履歴として維持できます。RESTとarchiveへ返すときは、そのprincipalの現在の代表identityを使い、内部IDは
公開しません。

schema 22から23へのmigrationは、保存済みの各ノートについて現在版一件を``imported``として作ります。
存在しない過去版や変更者を推測しません。文書書庫からの取り込みも、取り込んだ現在版を同じ基準点として
扱います。

=== 閲覧と認可

履歴一覧は本文を含めず、revision、変更時刻、変更者、変更種別だけを返します。個別の版を選んだ場合だけ
原文を返します。通常のノートでは現在の所有者とACLを適用し、現在の実効アクセス水準を返します。
共有を取り消した利用者は過去に閲覧できた版も読めません。削除済みノートの履歴は、30日の保持期間中も
所有者だけが読めます。過去のACLを保存しないことで、以前の共有先identityを現在の閲覧者へ開示しません。

=== 差分と復元

二つの版の差分は保存せず、要求時にAsciiDoc原文から行単位のUnified Diffを生成します。構文の装飾に使う
UTF-8 byte spanとは目的と寿命が異なるため、同じ記録へまとめません。

過去版の復元は履歴や現在版を上書きせず、その原文を現在のAdocWeaveとnote profileで再検証して、新しい
revisionとして保存します。現在の文献ライブラリで引用を解決し、現在のrevisionを``If-Match``で要求します。
ACL、所有者、作成日時、作成経路は過去へ戻しません。削除済みノートは先に通常の復元を行ってから、本文の
版を選びます。

=== archiveと文書書庫

日次archiveは災害復旧後も版履歴を失わないよう、保持中の全履歴を含めます。archiveは各履歴の変更者と
確認者を代表identityで表し、内部IDを保存しません。取り込み前にrevisionの重複、連続性、現在版との一致、
各版のAsciiDoc原文を検証し、空のdatabaseへ一つのtransactionで復元します。

``export-documents``は他の道具で現在の文書を読むための可搬出力であり、版履歴を含めません。
``import-documents``は入力した現在版一件を``imported``履歴として開始します。完全な災害復旧にはarchive、
外部編集と受渡しには文書書庫を使います。

== 帰結

各版の読み取り、任意の二版の比較、過去の本文の復元は、前の版を順番に適用せず実行できます。破損箇所の
特定とarchiveの検証も単純になります。将来の添付ファイルは``(note_id, revision)``へ参照集合を結び付け、
現在版と保持中の履歴のどちらからも参照されなくなった内容だけを削除できます。

一方、本文を毎回保存するため、差分だけを保存する方式より容量を使います。想定する約1,000ノートと
512 KiBの本文上限では、復元処理と保守試験の単純さを優先します。実際のdatabase容量と履歴件数を
運用で確認し、保持上限や間引きは測定結果が必要になった場合だけ再検討します。

== 代替案

=== 直近N件だけを保持

容量は制限できますが、必要な版が更新頻度によって失われ、archiveからの復旧可能範囲も不明確になります。
実測前に保持数を決める必要がないため、採用しません。

=== 差分を連鎖して保存

保存量を減らせますが、古い版の読取りと復元が後続する全差分の正しさへ依存します。途中の破損、形式変更、
任意の二版の比較、archive検証が複雑になるため、採用しません。

=== 過去のACLも版ごとに保存

当時の閲覧範囲を再現できますが、現在は共有を取り消した利用者やidentityを履歴から開示する危険があります。
履歴は監査記録ではなく本文の確認と復元を目的とするため、採用しません。

== 再検討条件

* 代表的な運用データで、完全な状態の保存がdatabase容量またはbackup時間の支配的な要因になった場合
* 法令や運用要件として、過去時点のACLを含む改ざん検知可能な監査記録が必要になった場合
* 添付ファイルの実装で、版と参照内容の保存期間をこの決定だけでは一貫して扱えない場合
