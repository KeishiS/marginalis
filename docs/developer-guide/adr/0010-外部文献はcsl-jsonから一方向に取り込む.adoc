= 外部ツールの文献情報はCSL-JSONから一方向に取り込む

[#top]
* 状態: 採用
* 日付: 2026-08-05
* 関連Issue: \#225
* 補足対象: xref:0004-文献ライブラリを利用者ごとに管理する.adoc#top[ADR 0004]

== 背景

Marginalisの文献ライブラリには、Web UI、REST API、MCPからCSL-JSONを登録できます。しかし、
Zoteroなどに既に蓄積した文献をまとめて持ち込み、外部側の更新を再び取り込む契約はありません。
一括登録だけを追加すると、同じ項目の判定、両方で変更した場合の扱い、citation keyの維持、入力から
消えた項目の扱いが利用者ごとの判断になります。

現在の文献項目は、所有者内で変わらない内部IDと、AsciiDocの``cite:``から参照するcitation keyを
分けています。citation keyはCSL-JSONの``id``ですが、外部サービスをまたいだ不変の識別子とは
扱いません。DOIやISBNなども重複候補の検出には使えますが、それだけで同じ文献だと断定して
上書きすると、別版や別媒体を誤ってまとめる可能性があります。

外部APIとの直接接続や双方向同期には、認証情報の保存、外部側の更新権限、失敗からの再開、削除の
伝播が必要です。まず、利用者が内容を確認でき、秘密情報を保存しない経路から始めます。

== 決定

最初の外部連携は、外部ツールから書き出したファイルをMarginalisへ一方向に取り込む方式とします。
取り込みは事前確認と適用の二段階に分け、事前確認だけではdatabaseを変更しません。

=== 方向と接続方法

* Marginalisから外部ツールへは書き戻しません。
* 利用者がCSL-JSONファイルを指定して取り込みを開始します。Marginalisは外部サービスへ接続せず、
外部サービスの認証情報を保存しません。
* 入力から消えた項目は、文献ライブラリから削除せず、取込元との対応も自動では外しません。
削除は既存の所有者向け操作と引用中の項目を保護する規則に従います。
* ファイル名や取込元の表示名は同一性の根拠にしません。

=== 入力形式

正式な入力はCSL-JSONの項目配列だけとします。BibTeXや外部サービス固有の形式は、検証済みの
CSL-JSONと後述する取込元情報へ変換するadapterとして別に設計します。変換器をMarginalisの
サーバー上で任意に実行せず、任意のCSLスタイルや``.bst``も実行しません。

各項目は現行の文献入力と同じ規則で検証し、欠けた題名、著者、発行年、識別子を推測しません。
入力全体の件数と大きさには上限を設け、拒否する項目は配列内の位置と理由を事前確認結果へ示します。

=== 取込元と項目の対応

取込元と文献項目は別の保存対象とします。

* *取込元*: 所有者、変更しない内部ID、方式、利用者向け表示名、revision、作成日時、最終取込日時
* *項目の対応*: 取込元ID、外部項目ID、文献項目の内部ID、最後に取り込んだCSL-JSONの要約値、
そのときの文献項目revision

一つの文献項目に複数の取込元を対応させられるようにします。同じ所有者、取込元ID、外部項目IDの
組は一意とし、一つの文献項目だけを指します。archiveには取込元と対応を含めますが、元のファイル、
外部サービスの認証情報、事前確認中の一時データは含めません。

CSL-JSONの``id``は、Marginalisでは引き続きcitation keyとして扱います。汎用CSL-JSONファイルだけでは
外部ツール固有の不変IDを保証できないため、最初のadapterは``id``をその取込元内の外部項目ID候補として
使います。再取り込みで``id``が変わった場合は同一項目と自動判定せず、DOIなどを重複候補として示して
利用者の選択を求めます。将来の外部サービス固有adapterは、サービスが明示する項目IDを渡せます。

ADR 0004は取込元の種類と外部IDを文献項目へ直接保存するとしていました。本決定では、複数の取込元を
一つの文献項目へ安全に対応させるため、独立した対応として保存する形へ補足します。

=== 事前確認と競合

事前確認は各入力を次のいずれかへ分類します。

* 新規作成
* 外部側だけが変わった既存項目の更新
* 前回と同じ内容で変更なし
* Marginalis側だけが変わっているため保持
* 両方が変わった競合
* citation key、外部項目ID、必須情報などが不正なため拒否

要約値は、検証後のCSL-JSONについてobjectのkey順を正規化したUTF-8表現から求めるSHA-256とします。
これは内容の比較に使う値であり、文献情報を復元する代わりには使いません。

取込元との対応がある項目では、保存した要約値と文献項目revisionを共通の基準として使います。
外部入力の内容とMarginalis側のrevisionがどちらも基準から変わった場合は、外部側で自動上書きしません。
利用者は項目ごとにMarginalis側を保持するか、外部側を採用するかを明示します。DOI、ISBN、arXiv ID、
題名などが一致するだけの項目は重複候補として示し、自動では統合しません。

適用時には、事前確認で読んだ文献項目revisionと取込元のrevisionを再確認します。一件でも変わって
いれば全体を変更せず、改めて事前確認を求めます。適用する作成、更新、取込元との対応は一つの
transactionで保存します。利用者は拒否された項目を計画から除外できますが、選択した計画の一部だけを
保存する部分的な成功は認めません。選択した範囲に未解決の競合が残る計画も適用しません。

=== citation keyと引用の保護

取込元との対応がある既存項目では、再取り込みによってcitation keyを変更しません。外部入力の``id``が
変わっていても、文献情報の更新には現在のcitation keyを使います。新規項目では入力の``id``を使用し、
所有者のライブラリ内で重複する場合は事前確認で拒否します。

citation keyの変更が必要な場合は、引用中のノートを同じtransactionで検査する専用操作として
取り込みから分離します。取り込みはノート本文を書き換えません。入力から項目が消えた場合も削除しない
ため、既存ノートが引用している文献を一方向の取り込みで失うことはありません。

=== schema更新との順序

取込元と項目の対応にはSQLite schemaとarchive形式の変更が必要です。通常のschema更新として実装し、
schema番号を再開始する\#105とは組み合わせません。\#105の判断は、\#232で追加するノートの来歴と人手確認を
含む保存形式が確定した後に行います。外部文献の取り込みは、その判断を待たず、現行archiveからの移行を
用意した後続版で公開できます。

== 結果

利用者は外部サービスの認証情報をMarginalisへ渡さず、変更内容を確認してから文献情報を持ち込めます。
再取り込みでは外部側だけの変更を識別でき、両方で変更した項目は利用者の判断なしに上書きされません。
内部ID、citation key、外部項目IDの役割を分けるため、外部側の識別規則が変わっても引用を暗黙に
付け替えません。

取込元、対応、要約値、基準revisionを保存するため、schemaとarchiveが大きくなります。汎用CSL-JSONの
``id``が変わった場合は自動追跡できず、利用者による重複候補の解決が必要です。ファイルの再選択も利用者が
行うため、定期的な自動同期にはなりません。

== 代替案

=== 最初から外部APIへ接続する

差分取得や安定した外部項目IDを利用しやすくなりますが、サービスごとの認証情報、権限、API停止、
rate limit、削除の伝播を同時に扱う必要があります。ファイル取り込みの競合規則を確認する前に
秘密情報と外部更新を追加しないため、採用しません。

=== 双方向に同期する

一か所で直した内容を双方へ反映できますが、外部側の同時更新、共有ライブラリの権限、書き戻し失敗、
削除の扱いが必要です。Marginalisを外部ライブラリの更新主体にしない最初の段階では採用しません。

=== DOIなどで自動的に統合する

取込元の対応がなくても重複を減らせますが、別版、訂正版、書籍と章などを同一項目へ誤ってまとめる
可能性があります。外部IDは候補表示にだけ使い、利用者の選択なしに統合しません。

=== 入力に存在しない項目を削除する

外部側の完全な複製になりますが、部分的な書き出しや絞り込んだファイルを読み込んだだけで引用中の
項目を失う可能性があります。明示的な削除と引用検査を迂回するため採用しません。

=== 取り込みのたびに外部側を優先する

規則は単純ですが、Marginalis側で修正した内容を確認なしに失います。共通の基準から双方が変わった
場合は競合として止めます。

== 再検討条件

* ファイルの再選択が運用上の負担となり、自動取得が必要になった場合
* 採用する外部サービスと、認証情報の保存・失効・暗号化要件が確定した場合
* 外部側への書き戻しを必要とする具体的な編集手順と権限モデルが確定した場合
* 部分適用が必要な件数と、失敗後に安全に再開する識別方法を実測できた場合
* 外部サービスが削除済み状態を安定して提供し、引用中の項目を保護した削除確認を設計できた場合
