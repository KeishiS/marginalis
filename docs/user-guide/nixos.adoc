= NixOSでの運用

[#top]
この文書は、NixOSでMarginalisを配備・運用する人に向けて、設定、秘密情報、データの保存、
バックアップ、復元、問題発生時の確認方法を説明します。以前のバージョンから更新する場合は、
https://github.com/KeishiS/marginalis/releases[GitHub Releases]の該当版のRelease Notesも
確認してください。

== 基本設定

[source,nix]
----
services.marginalis = {
  enable = true;
  baseUrl = "https://notes.example.test/marginalis";
  listenAddress = "127.0.0.1:3000";
  backupDirectory = "/srv/marginalis-backups";
  backupRetention = 30;
  restoreCheck.enable = true;
  oidc = {
    issuerUrl = "https://id.example.test/oauth2/openid/marginalis";
    clientId = "marginalis";
    clientSecretFile = "/run/secrets/marginalis-oidc-client-secret";
    caCertificateFile = "/run/secrets/marginalis-kanidm-ca.pem";
  };
  mcp = {
    enable = true;
    allowedOrigins = [ "https://chatgpt.com" ];
  };
};
----

``services.marginalis.enable = true;``にすると、サービスが使用する``services.marginalis.package``と
同じパッケージの``marginalis``管理コマンドをシステムの``PATH``へ追加します。別途
``environment.systemPackages``へ追加する必要はありません。反映後は次のコマンドで版を確認できます。

[source,sh]
----
/run/current-system/sw/bin/marginalis --version
----

== binary cacheからの取得

リリースタグ(``v*``)の検証が成功するたびに、CIがそのタグのx86_64-linuxとaarch64-linuxの
実行パッケージをbuildしてbinary cache(``keishis.cachix.org``)へpushしています。利用側の
NixOS設定へ次を追加すると、``nixos-rebuild``はbuildせずclosureの取得だけで更新できます。

[source,nix]
----
nix.settings = {
  substituters = [ "https://keishis.cachix.org" ];
  trusted-public-keys = [
    "keishis.cachix.org-1:j3UwGrrgTifYMa9Uo6fyDU8GEJBcorOzrHdkXBXruK4="
  ];
};
----

cacheへ一致(hit)するのは、CIがbuildしたものと同一のderivationだけです。利用側のflakeで
``inputs.marginalis.inputs.nixpkgs.follows = ...``のようにinputを上書きするとderivationが
変わり、cacheへ一致しなくなるため、marginalisのflake.lockのまま取り込んでください。
参照するrevisionはリリースタグを指定します。タグ以外のcommitを指した場合はcacheへ
一致せず、従来どおり利用側でbuildされます。

古いタグのcacheを手動で消す運用は不要です。同じ内容のstore pathは版をまたいで共有される
うえ、容量の上限へ達した場合はCachixが利用の古いpathから自動で回収します。

== 秘密情報とデータの保存先

``clientSecretFile`` は systemd credential として渡され、Nix store に現れてはなりません。内部 CA の
Kanidm を使う場合は ``caCertificateFile`` に PEM trust anchor を指定し、OIDC Discovery と token exchange
に適用します。
SQLiteデータベースは``dataDir``（既定値``/var/lib/marginalis``）直下の``marginalis.sqlite``に固定します。
任意のdatabase URLは指定できません。正本を別volumeへ置く場合は、``dataDir``自体をその絶対pathへ
変更してください。現行のSQLite schema versionは23です。旧versionを起動時に自動移行しません。

schema 22より前のdatabaseから更新する場合は、更新前の実行環境で``export-archive``を実行し、
その書庫を現行の``restore-archive``で空のschema 23へ取り込んでください。``restore-archive``は
変換・隔離databaseでの復元検証・取り込みを一括で行います。取り込める旧archiveの範囲は
<<以前のarchiveからの移行>>を参照してください。
同期cursorと変更索引、MCPの認可状態、client登録とtokenはarchiveへ含まれないため、更新後に
外部検索サービスとMCPクライアントを接続し直します。
schema 22以降の更新は<<SQLite-schemaの更新>>の手順でSQLite全体を退避してから前進migrationします。

reverse proxyは``/auth/``、``/api/``、``/mcp``、``/.well-known/``を同一オリジンへ転送します。
サブパスでは通常endpointの外部prefixをupstreamへ渡す前に除去します。一方、RFC 8414/9728の
``/.well-known/`` URLはhost rootから始まりsubject pathを末尾に持つため、pathを除去せずupstreamへ渡します。
``baseUrl`` と OIDC redirect URI は一致させます。
``mcp.allowedOrigins`` は HTTPS origin の完全一致であり、path、query、userinfo を含む値や HTTP origin は
起動時に拒否されます。

MCPを有効にすると、内蔵Authorization Serverのissuerと各endpointを``baseUrl``から自動的に導出します。
外部Authorization Serverのissuerやclaim名は設定しません。詳しい接続方法は
xref:mcp.adoc#top[MCPへの接続と認可]を参照してください。

IdPのdiscoveryに失敗した場合、serviceは動作したままログインだけができません。起動失敗より
気付きにくいため、``oidc.discovery.failed``を監視対象へ含めてください。

== IdPから受け取る利用可否の情報

Marginalisは標準のOIDC IdPで利用者を認証します(参照実装はKanidm 1.10)。OIDC callbackでは
署名検証済みID tokenの設定したclaim(既定``groups``)を読み、設定した許可値の一覧
(既定``server-users``)のいずれも含まれなければログインを拒否します。サーバー全体の
管理者グループは使用しません。IdP側のグループ変更は次回のOIDC loginから反映され、既存の
Web sessionとMCP tokenは有効期限または明示的な認可取消までlogin時のidentityを保持します。
Web session は最終利用から24時間で失効し、ログインから7日を絶対期限とする。継続利用中は
アイドル期限だけを延長するため、group変更を直ちに反映する必要がある場合は、対象利用者に再ログインを
依頼するか、7日の絶対期限まで待つ。

利用可否の判定は次のoptionで調整できます。既定値は参照実装(Kanidm)向けで、既定のままなら
従来の配備と同じ動作です。

* ``oidc.groupClaim`` — 判定に使うclaim名(既定``groups``)
* ``oidc.allowedClaimValues`` — 許可する値の一覧(既定``["server-users"]``)。いずれか1つに
  一致すれば許可します。明示的に空の一覧を設定した場合は、issuerで認証できた利用者を全員
  許可します(IdP側でclientの利用者を絞る運用向け)
* ``oidc.scopes`` — ``openid``以外に要求するscope(既定``["profile" "email" "groups_name"]``)
* ``oidc.allowedAlgorithms`` — 許可するID token署名方式(既定``["ES256"]``)。``RS256``の追加は
  ADR 0015の依存脆弱性判断の更新が前提です
* ``oidc.tokenEndpointAuth`` — token endpointのclient認証方式(既定``client_secret_post``)

=== 参照実装: Kanidm

KanidmのOAuth2 clientは``groups_name`` scopeを許可し、文字列配列の``groups`` claimに
``server-users``を含めるよう設定します。

[source,bash]
----
kanidm system oauth2 add-redirect-url marginalis \
  https://marginalis.sandi05.com/auth/oidc/callback
kanidm system oauth2 update-scope-map marginalis \
  server-users openid profile email groups_name
----

redirect URI がすでに登録済みなら最初のコマンドは不要です。Marginalis は Kanidm REST API を照会しないため、
service account、API token、custom ACP は不要です。

=== 例: Googleアカウントで特定のメールアドレスだけを許可する

グループclaimを発行できないIdPでは、``email`` claimと許可するメールアドレスの一覧で利用者を
絞れます。判定claimが``email``の場合は、ID tokenの``email_verified``がtrueであることも要求します。
GoogleのID token署名はRS256のみのため、``allowedAlgorithms``の明示が必要です(ADR 0015の
依存脆弱性判断を先に確認してください)。

[source,nix]
----
services.marginalis.oidc = {
  issuerUrl = "https://accounts.google.com";
  clientId = "…….apps.googleusercontent.com";
  clientSecretFile = "/run/secrets/marginalis-oidc-client-secret";
  scopes = [ "email" ];
  allowedAlgorithms = [ "RS256" ];
  groupClaim = "email";
  allowedClaimValues = [ "alice@gmail.com" ];
};
----

== Webhook通知の運用

利用者が登録したWebhookの配送は、``marginalis.service``の中の常駐workerが行います。専用のserviceや
timerはありません。利用者向けの登録手順と通知の内容は xref:webhooks.adoc#top[Webhook通知]を
参照してください。

送信先は既定で公開networkのHTTPS（port 443）だけを許可し、private addressへの送信を登録時と
送信直前の両方で拒否します。自分が管理するnetwork内の受信サーバーへ配送したい場合だけ、
``webhook.allowedHosts``へそのhost名を列挙します。列挙したhostはHTTP、任意のport、
private addressも許可されるため、管理下にない名前を書かないでください。

[source,nix]
----
services.marginalis.webhook.allowedHosts = [ "receiver.internal.example" ];
----

配送の失敗は``webhook.delivery.failed``、再試行の上限による購読の停止は
``webhook.subscription.disabled`` eventで記録します。ログにはwebhook IDと失敗分類だけが残り、
送信先URLと署名secretは残りません。詳細は
xref:../developer-guide/observability.adoc#top[ログと障害診断]を参照してください。

== 定期処理

* ``marginalis-purge-expired.timer`` は毎日実行され、30 日を超えたソフトデリート済みノートと、どの版からも
参照されないまま30日を超えた添付画像を削除します。期限切れ・失効済みのWeb/OIDC認証状態、MCPの認可codeと
token、参照されない古いclientも削除します。
保持期間の7日を過ぎた配送済み・破棄済みのWebhook配送記録も同時に削除します。
* ``backupDirectory``を設定すると``marginalis-backup.timer``が毎日実行されます。単一のSQLite read
transactionからsnapshotを取得するため、HTTP serviceを停止しません。
* 成功世代は``backup-<Unix時刻ミリ秒>``というディレクトリで、``marginalis-archive.json``と
``COMPLETE``を含みます。archiveの検証が完了するまで``COMPLETE``は作成されません。
* ``backupRetention``は検証済み成功世代の保持数で、既定値は30です。保持処理は
``backupDirectory``を正規化し、その直下にある既定名・marker・archiveをすべて検証できた世代だけを
対象にします。不完全な世代、symlink、運用者が置いたファイルは数えず、削除もしません。
* ``restoreCheck.enable = true``を明示すると、最新成功世代を隔離した空の一時databaseへ復元して
再exportとの論理一致を調べる``marginalis-restore-check.timer``が有効になります。既定scheduleは
各四半期の最初の土曜日3時です。``restoreCheck.calendar``で変更できます。

保存媒体のsnapshot、off-site複製、暗号化はhost側で構成します。30世代に加え、復元用の一時databaseと
SQLiteの一時領域を確保してください。必要量の目安は、正本と最大archiveの合計に作業余裕を加えた容量です。

== バックアップの確認

archive単体の検証と、隔離復元の検証を手動で実行できます。どちらもノート本文を標準出力やlogへ出しません。
現行archiveは``marginalis-archive-18``で、AdocWeave package版``0.41.0``とnote profile版``6``を記録します。
形式またはいずれかの版が実行中のMarginalisと一致しないarchiveは、databaseを変更する前に拒否されます。
同じ段階で、利用者の代表identityとalias、ノートの識別子、所有者、revision、日時、本文、ACLの参照先と
重複に加え、保持中の全版についてrevisionの連続性、現在版との一致、変更者、AsciiDoc原文も検証します。
添付画像は、形式、容量、SHA-256、ノートへの所属、各版の本文が参照する画像集合との一致を検証します。
本文から参照索引を再構築した後に復元計画が確定するため、検証に失敗した内容の一部だけがdatabaseへ
書き込まれることはありません。

[source,sh]
----
sudo -u marginalis marginalis validate-archive \
  --input /srv/marginalis-backups/backup-<時刻>/marginalis-archive.json
sudo systemctl start marginalis-restore-check.service
sudo journalctl -u marginalis-backup.service -u marginalis-restore-check.service
----

backup作成または検証が失敗した場合、保持処理は実行されず、既存の成功世代は残ります。破損した成功世代を
保持処理が検出した場合も削除前に失敗します。容量不足、権限、mount状態、SQLite errorを上記journalと
``systemctl status``で確認し、原因を直してから再実行してください。不完全なディレクトリを削除する場合は、
``COMPLETE``がないことと対象pathが``backupDirectory``直下であることを運用者が確認します。

[[SQLite-schemaの更新]]
== SQLite schemaの更新

schema 22以降は、日次archiveから空のdatabaseを作り直すのではなく、``migrate-database``で既存の
SQLite databaseを次のschemaへ進めます。このcommandはWeb session、MCP token、同期cursor、
Webhook配送状態を含むSQLite全体を退避するため、論理データだけを持つ日次archiveと目的が
異なります。

``marginalis-migrate-database.service``は``backupDirectory``を設定した場合だけ利用でき、自動起動
しません。リリースノートがschema migrationを指示したときは、次の順で実行します。

[source,bash]
----
sudo systemctl stop marginalis.service
sudo nixos-rebuild switch --flake <利用中のflake>
sudo systemctl start marginalis-migrate-database.service
sudo journalctl -u marginalis-migrate-database.service -o cat -n 50
sudo systemctl start marginalis.service
----

unitは通常serviceと同時に実行せず、``backupDirectory``に
``database-migration-<Unix時刻ミリ秒>.sqlite3``を上書きせず作成します。退避にはWAL内の
確定済みデータも含みます。権限0600、SQLiteの整合性、外部キーとschema履歴を検査し、
退避を永続的に確定できた後だけ、すべての必要なmigrationを1つのtransactionで適用します。
容量不足、退避先の重複、履歴の欠番、schema 22より前の版の場合はdatabaseを変更せず失敗します。

現在のschemaは23です。schema 22から更新する場合は、すべての外部identityを推測でまとめず、
``issuer``と``subject``が完全に一致する組ごとに内部principalを作ります。Web session、MCP token、
Webhookのeventと配送状態を含む既存行は、そのprincipalへの参照へ移します。同期用とWebhook用で
別々だった変更番号を一つへ統合するため、既存の同期cursorと変更索引は移行しません。連環などの
外部検索用投影は、移行後にcursorを省略した全量同期から再開してください。すでにschema 23で
未適用のmigrationがない場合は、成功logの``applied_migrations=0``と``backup=none``で何も変更しなかった
ことを示し、SQLite退避も作りません。schema 22には過去版がないため、各ノートの移行時の現在版を
``imported``という変更種別の履歴一件として開始します。存在しない版や変更者は推測しません。

移行後は``marginalis-diagnose.service``、HTTP health、OIDC login、MCP認可を確認します。切戻しが必要な
場合は、新しいserviceを停止し、移行後のdatabaseを別名で保全してから、SQLite退避と移行前の
NixOS generationを組にして戻します。退避のdatabaseだけを新しい実行ファイルと組み合わせると、旧schemaを
再び拒否するため起動できません。

[[OIDC-issuerの移行]]
== OIDC issuerの移行

認証サービスを移す場合は、古い``(issuer, subject)``と新しい``(issuer, subject)``を、同じ利用者を表す
一つのprincipalへ明示的に結び付けます。メールアドレス、表示名、claimの一致から自動では判断しません。
新しい組は、認証サービスの管理画面または検証済みのID tokenで事前に確認してください。

次の例では、操作前のSQLite全体を権限0600で退避し、新しいidentityをaliasとして追加すると同時に
代表identityへ変更します。serviceを停止した状態で実行してください。

[source,bash]
----
sudo systemctl stop marginalis.service
sudo -u marginalis env \
  MARGINALIS_DATABASE_URL=sqlite:/var/lib/marginalis/marginalis.sqlite \
  marginalis link-identity \
  --existing-issuer 'https://old-id.example.test' \
  --existing-subject '<以前のsubject>' \
  --new-issuer 'https://new-id.example.test' \
  --new-subject '<新しいsubject>' \
  --make-primary \
  --backup-directory /var/lib/marginalis-backups
----

commandは、既存identityが見つからない場合、二つが同じ場合、または新しいidentityが別のprincipalに属する
場合に、databaseを変更せず失敗します。入力とdatabaseの事前検査に成功すると、
``identity-link-<Unix時刻ミリ秒>.sqlite3``を上書きせず作成し、退避の整合性を確認してから一つの
transactionで結び付けます。ログにはissuer、subject、内部IDを記録しません。

代表identityだけを後から変更する場合は、すでに同じprincipalへ結び付いているidentityを指定します。

[source,bash]
----
sudo -u marginalis env \
  MARGINALIS_DATABASE_URL=sqlite:/var/lib/marginalis/marginalis.sqlite \
  marginalis set-primary-identity \
  --issuer 'https://old-id.example.test' \
  --subject '<以前のsubject>' \
  --backup-directory /var/lib/marginalis-backups
----

引き継ぎ後にNixOSのOIDC設定を新しいissuerへ変更し、serviceを起動します。新旧identityはノート、ACL、
文献、同期、MCPのscope上限と失効を同じ利用者として扱います。既存のWeb sessionとMCP tokenは、発行時に
認証したidentityを保持します。日次archiveは代表identityとaliasの対応を保存するため、復元後も結び付けを
保ちます。

serviceを再開する前に切り戻す場合は、変更後のdatabaseを別名で保全してから、commandが作成したSQLite
退避を戻します。再開後に新しいデータを書き込んだ場合は、その退避を戻すと新しい変更も失われます。
その場合は``set-primary-identity``で以前のidentityを代表へ戻し、OIDC設定を戻してください。

[[以前のarchiveからの移行]]
== 以前のarchiveからの移行

現行版が直接取り込めるのは、現行の保存契約と、その直前に公開された保存契約だけです(設計判断は
xref:../developer-guide/adr/0018-archiveは直前の公開済み保存契約からだけ移行する.adoc#top[ADR 0018]を
参照してください)。保存契約は、archive形式、AdocWeave package版、note profile版の3項目の組です。
アプリケーションの版が上がっても、この組が変わらなければ同じ保存契約として扱います。

現行契約のarchiveは変換なしで``import-archive``できます。直前契約のarchiveは、
``migrate-archive``で現行契約へ変換してから取り込みます。

[source,sh]
----
sudo -u marginalis marginalis migrate-archive \
  --input /srv/marginalis-migration/archive-previous.json \
  --output /srv/marginalis-migration/archive-current.json
sudo -u marginalis marginalis verify-restore \
  --input /srv/marginalis-migration/archive-current.json
----

変換では全ノートを現行のAdocWeaveの規則で再検証します。入力archiveは変更されず、出力先が既に
存在する場合は上書きしません。失敗した場合のエラーに示す``position``は、archiveの``notes``または
``note_acl``配列内の1から始まる位置で、本文や識別子は診断へ出力されません。

変換・検証・取り込みを一括で行う場合は、``migrate-archive``と``verify-restore``、
``import-archive``の3段のかわりに``restore-archive``を使えます。書庫が現行契約ならそのまま、
直前契約なら変換したうえで、隔離databaseでの復元一致を検証してから
``MARGINALIS_DATABASE_URL``のdatabaseへ取り込みます。中間ファイルは残りません。

[source,sh]
----
sudo -u marginalis marginalis restore-archive \
  --input /srv/marginalis-migration/archive-previous.json
----

[[保存契約の履歴]]
=== 保存契約の履歴

直前契約より古いarchiveは、次の表で現行へ持ち上げるために使うリリースと出力契約を確認します。
過去の実行環境はhttps://github.com/KeishiS/marginalis/releases[GitHub Releases]から取得します。
通常運用の秘密情報やネットワークへ接続せず、移行対象のarchiveと出力先だけを渡してください。

表は、現在の3項目を持ち、現行の``migrate-archive``まで段階的な移行経路が続くv0.8.0以降を記録します。
「初回・採用版」は、その3項目の組を初めて書き出した公開版と、その後に同じ組を書き出したタグの
範囲です。これにより、archive内の3項目から移行に必要な実行版を選べます。v0.43.0はタグだけが作られ、GitHub Releaseは
公開されていないため、同じ契約を使う最初の公開済みリリースはv0.44.0です。

保存契約を変更した開発中の状態は「未公開」と記録します。リリース時には、リリース手順に従って
この欄を実際の公開版へ置き換えます。したがって、公開済みの各組には必ず初めて書き出した版が
一つ記録されます。``marginalis-archive-18``は代表identityとalias群、保持中の全版、添付画像のbytesと
各版の参照集合を含みます。

v0.45.0は、v0.8.0以降の表にある旧契約を``marginalis-archive-17`` / 0.40.1 / 5へ変換できる
最後の公開版です。Nixでv0.45.0を固定して構築し、入力とは別のファイルへ変換します。

[source,sh]
----
nix build 'github:KeishiS/marginalis/v0.45.0#default' \
  --out-link ./marginalis-v0.45.0
./marginalis-v0.45.0/bin/marginalis migrate-archive \
  --input /srv/marginalis-migration/archive-old.json \
  --output /srv/marginalis-migration/archive-0.40.1.json
----

たとえばv0.18.0のarchiveは、この操作で``marginalis-archive-17`` / 0.40.1 / 5へ変換し、その出力を
v0.46.0またはv0.47.0の``migrate-archive``へ渡します。その出力である
``marginalis-archive-17`` / 0.41.0 / 5を現行版の``restore-archive``へ渡すと、直前契約として受理し、
``marginalis-archive-18`` / 0.41.0 / 6へ変換して復元します。

ADR 0018の採用後に保存契約を変更する場合は、直前の公開済み保存契約から新契約への変換を必ず
同じリリースへ含めます。以後は表の移行経路を順番に辿ることで、契約を1件ずつ持ち上げられます。

== 他の道具で読める形での取り出し

保存しているノートと文献情報を、Marginalis以外の道具で読める形へ一度に書き出せます。ノートは
保存しているAsciiDocのまま``.adoc``ファイルへ、文献情報はCSL-JSONの配列へ書き出します。CSL-JSONは
pandocやZoteroなど多くの文献管理ツールが読み取る形式です。

[source,sh]
----
sudo -u marginalis marginalis export-documents \
  --output /srv/marginalis-export/2026-07-31.tar.xz
----

出力は``tar.xz``形式の書庫1つです。展開すると、出力ファイル名から作った最上位ディレクトリーの下に
所有者ごとの内容が並びます。引用は作成者のライブラリで解決するため、この分け方でノートと
文献の対応が保たれます。

[source,text]
----
2026-07-31/
  id.example.test/alice/notes/先行研究の整理-019f0000-….adoc
  id.example.test/alice/bibliography.json
  manifest.json
----

[source,sh]
----
tar -xJf /srv/marginalis-export/2026-07-31.tar.xz
----

ファイル名は題名とnote IDを並べた形です。題名が重複しても、ファイル名に使えない文字を含んでも、
note IDを付けるため衝突しません。削除済み（ソフトデリート）のノートは書き出しません。
``cite:``は解決せず本文のまま書き出すため、受け取った側の道具が同じ出力のCSL-JSONで解決できます。
この文書書庫は他の道具で読むための形式であり、CSL-JSONの取込元、外部項目との対応、前回取込時の
hashは含みません。それらを含む復元用の退避には``export-archive``を使用してください。文書書庫を
取り込んだ後に同じCSL-JSONを指定する場合は、新しい取込元として事前確認します。

現在版の本文が参照する添付画像は、所有者ごとの``attachments/``へ元のbytesのまま書き出します。
manifestに記録したバイト数とSHA-256が一致しない画像は取り込みません。過去版だけが参照する画像を含む
完全な復元には``export-archive``を使用してください。

``manifest.json``は、各ファイルとnote IDの対応、所有者、日時、revision、タグ、ACL、添付画像に加えて、
形式名``marginalis-documents-3``、Marginalisの版、解析に使ったAdocWeave packageの版、ノートの
受理規則の版、作成経路、人手確認記録、書き出し時の本文・所有者・ACL・添付画像を結び付けた
``state_sha256``を持ちます。版の意味はarchiveと同じです。取り込む側は、稼働しているMarginalisの版と
比べて再検証や移行が必要かどうかを判断できます。``state_sha256``は外部編集を検出する値であり、
署名や改ざん防止の機能ではありません。

出力先のファイルが既に存在する場合は失敗します。書庫ファイルは``600``で作成し、書庫の中の
ディレクトリーは``700``、ファイルは``600``として記録します。展開する側の設定によらず、所有者だけが
読める状態になります。

=== 書き出した内容を取り込む

書き出した書庫は``import-documents``で取り込めます。別の道具で``.adoc``ファイルを編集してから戻す
場合と、別の環境へ移す場合に使います。

[source,sh]
----
sudo -u marginalis env \
  MARGINALIS_DATABASE_URL=sqlite:/srv/marginalis-restore/marginalis.sqlite \
  marginalis import-documents --input /srv/marginalis-export/2026-07-31.tar.xz
----

本文の正は``.adoc``ファイル、識別子、所有者、日時、revision、ACLの正は``manifest.json``です。
manifestが挙げるファイルが無い場合は失敗します。manifestに無いファイルは無視するため、
ファイルを置くだけではノートを増やせません。

``.adoc``の本文、manifestの所有者またはACLを変更した場合は、取り込み時にrevisionを1増やし、
更新日時を取り込み時刻へ進めます。以前に確認済みだったノートも現在の版では確認待ちになります。
変更していない文書はrevisionと確認状態を維持します。``state_sha256``を手で書き換えるとこの判定が
できなくなるため、編集しないでください。

manifestが記録するAdocWeave packageの版とノート受理規則の版が稼働中の値と違う場合は、全ノートを
現行の規則で再検証してから取り込みます。一件でも現行規則を満たさない場合はdatabaseを変更せず、
manifest内の位置で失敗を示します。診断へ本文や識別子は出力されません。

取り込み先は空のdatabaseに限ります。既存のノートまたは認証状態があるdatabaseへの取り込みは
失敗し、暗黙に上書きされません。書庫の展開では、``..``や絶対path、symlink、通常ファイルと
ディレクトリー以外の項目を拒否し、展開後の大きさにも上限を設けています。

*この出力はバックアップの代わりではありません。* 削除済みノートを含まないため、
日次の退避と復元には次節の``export-archive``と``import-archive``を使用してください。archiveだけが
Web sessionを除く全状態を検証付きで往復できます。

== 復元と切戻し

本番databaseへ直接importしてはいけません。次の手順では、先に別の空databaseへ復元し、確認後に
service停止中の切替を行います。

[arabic]
. 対象archiveを``validate-archive``と``verify-restore``で検証します。
+
[source,sh]
----
sudo -u marginalis marginalis verify-restore \
  --input /srv/marginalis-backups/backup-<時刻>/marginalis-archive.json
----
. ``dataDir``とは別の永続領域に空の復元先を作り、archiveをimportします。既存ノートまたは認証状態が
あるdatabaseへのimportは失敗し、暗黙に上書きされません。
+
[source,sh]
----
sudo -u marginalis env \
  MARGINALIS_DATABASE_URL=sqlite:/srv/marginalis-restore/marginalis.sqlite \
  marginalis import-archive \
  --input /srv/marginalis-backups/backup-<時刻>/marginalis-archive.json
----
. 復元先を再exportし、``validate-archive``で検証します。ノート数、所有者、削除状態、revisionを
運用上の期待値とも照合します。archiveはWeb sessionやMCP tokenなどの認証状態を含まないため、
切替後は再ログインと必要に応じたMCP再認可が必要です。
. maintenance windowでserviceを停止し、現在の``dataDir``を削除せず退避します。復元済みdatabaseを
新しい``dataDir``へ配置して所有者とmodeを確認した後、serviceを起動します。
. health、OIDC login、所有者・ACL共有先・対象外利用者の可視性、ソフトデリート状態、
MCP authorizationを確認します。

切戻しではserviceを再度停止し、復元後のdatabaseを別名で保全してから、手順4で退避した元の``dataDir``へ
戻します。復元先の確認が終わるまで元databaseを上書きまたは削除しないでください。

初回配備後は``GET /api/v3/health``、OIDC login、所有者・ACL共有先・対象外利用者の可視性、
MCP authorizationを確認します。

== 問題が発生したときの確認

公開livenessは``GET /api/v3/health``で確認します。この応答はHTTP processの稼働だけを表し、
外部IdPの一時的な停止では失敗しません。SQLiteと設定はserviceと同じ実行環境で診断します。

[source,bash]
----
curl --fail http://127.0.0.1:3000/api/v3/health
systemctl is-active marginalis.service
systemctl show marginalis.service -p InvocationID -p ExecMainStatus
systemctl show marginalis-purge-expired.service -p Result -p ExecMainStatus
systemctl show marginalis-backup.service -p Result -p ExecMainStatus
systemctl list-timers marginalis-purge-expired.timer
systemctl cat marginalis.service
systemctl start marginalis-diagnose.service
journalctl -u marginalis-diagnose.service -o cat -n 20
----

``diagnose``はSQLiteの読み取り可否、schema version、``PRAGMA quick_check``、
外部キー違反件数と、MCPの有効化を含む非秘密設定だけをJSONで出力します。全検査が正常な場合だけ
終了status 0です。
databaseを作成・移行せず、OIDC client secret、Cookie、token、ノート本文は出力しません。

設定の報告は``configuration.variables``に環境変数名を鍵として並びます。各項目の``set``は設定の有無、
``required``は現在の構成で必須かどうかを示します。``value``は秘密でも保存先でもない変数にだけ付き、
``element_count``はカンマ区切りの変数の要素数です。``configuration.mcp_enabled``はMCPを有効と判断した
結果で、``MARGINALIS_MCP_ENABLE``の値と一致します。
serviceの起動処理と``diagnose``は同じ宣言から値を読むため、両者の判断が食い違いません。
値の前後の空白は取り除いて扱い、空白だけの値は未設定とみなします。
``status``が``failed``の場合は``database.error``と各検査の``actual``、``expected``を確認します。
SQLを実行できなかった場合は、``database.failures``の``check``で失敗した検査、``category``で
ロック、読み取り専用、入出力エラーなどの分類を確認できます。``sqlite_code``はSQLiteが返した
数値コードです。schema版が古いだけの場合は``schema.ok``が``false``になりますが、
``database.failures``は出力されません。

安定したjournal event名、共通field、記録禁止情報、障害時の絞り込み方は
xref:../developer-guide/observability.adoc#top[ログと障害診断]を参照してください。監視や通知では、人向けのログ本文ではなく
``event``を使用します。

[source,bash]
----
journalctl -u marginalis.service --since today
journalctl -u marginalis.service _SYSTEMD_INVOCATION_ID="$(systemctl show marginalis.service -p InvocationID --value)"
journalctl -u marginalis-purge-expired.service -g 'maintenance.purge.'
journalctl -u marginalis-backup.service -g 'maintenance.backup.'
find /srv/marginalis-backups -mindepth 1 -maxdepth 1 -type d \
  -exec test -f '{}/COMPLETE' ';' -print | sort | tail
----

HTTP logは``request_id``で一連の処理を追跡できます。OIDC到達不能時もloginだけを503で閉じたまま
livenessを維持します。ノートのプレビューに成功したHTTP logでは、``note_diagnostic_count``が
保存を妨げない診断の件数を示します。
保守unitの失敗はHTTP serviceの停止を意味しません。unitの``Result``と同じinvocationのjournalを確認し、
保存先容量、権限、SQLite診断結果を修正してからunitを再実行します。
