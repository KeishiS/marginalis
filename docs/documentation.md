# 文書管理方針

## 目的と対象

この文書は、Marginalisの文書について対象読者、責務、正本、更新契機を定める開発者向けの
規範です。製品の動作そのものは定義せず、個別仕様の正本は[文書案内](README.md)から参照します。

## 配置と責務

| --- | --- | --- | --- |
| `README.md` | 初見の利用者・運用者・開発者 | 製品概要と最短の導線。詳細仕様の正本ではない | 製品の位置付けまたは主要導線の変更 |
| `CONTRIBUTING.md` | 人の開発参加者 | 参加方法の入口。詳細手順は`docs/development.md`を参照 | 寄稿手順または必須検証の変更 |

| `CHANGELOG.md` | 利用者・運用者 | 公開済みの利用者影響 | 各リリース |
| `docs/README.md` | 全読者 | 読者別の文書案内と正本の優先順位 | 文書の追加、移動、責務変更 |

## 文書冒頭の要件

新しい規範文書は冒頭で、対象読者、目的、対象外、正本として扱う範囲、関連文書を説明します。
短い案内文書では一つの段落へまとめても構いません。既存文書は内容を変更するときにこの形式へ
段階的に揃えます。版番号付きsnapshotへ遡及的な書式変更は行いません。

## 正本と不一致

製品要件は`requirements.md`、設計上の不変条件は`architecture.md`、公開REST wire契約は
`openapi.json`、各主題の利用・運用契約は主題別規範文書を正とします。schema、manifest、
コード上の定数は実装または配布物であり、確定要件より上位の正本とは扱いません。

要件、設計、公開契約、実装が一致しない場合は、優先順位で一方を正しいことにせず欠陥として
記録します。意図した契約を確認し、同じ変更で文書、機械可読な契約、実装、試験を一致させます。
READMEなどの概要、ロードマップ、Issue、版番号付きsnapshot、ヒアリング、研究文書は現行仕様の
代用にしません。

重複する説明は概要側を短くし、詳細の正本へリンクします。機械可読な契約を文章へ複製する場合は、
生成または整合検査を設けます。

## 情報種別の分離

- **現行仕様**: 現在の利用者・運用者向け動作と不変条件
- **設計判断**: 長期に参照する選択理由、代替案、再検討条件
- **将来計画**: ロードマップ上の方向、順序、公開単位
- **作業項目**: GitHub Issue上の背景、依存関係、動作例、完了条件
- **公開履歴**: CHANGELOGとGit tag上の文書
- **非規範履歴**: 版番号付きsnapshot、ヒアリング、研究上の考察

ADRを追加する場合は`docs/adr/NNNN-短い名称.md`とし、状態、日付、背景、決定、結果、代替案、
再検討条件を記載します。作業状況や一時的な計画はADRへ記載しません。

## 状態と用語

機能や契約の状態には「対応」「非対応」「条件付き対応」「廃止」を使用します。「保持」はデータや
履歴の保存期間にだけ使用します。識別子、HTTP header、設定名、コマンド、コード上の型名は原綴りを
使い、それ以外は自然な日本語で説明します。

## Issueと履歴

作業項目の正本はGitHub Issuesです。リポジトリ内にIssueファイルを追加しません。v0.5.0までの
ローカルIssueは[移行対応表](issue-migration.md)から、GitHub Issue、現行文書、または
`v0.5.0`タグ上の原文へ辿れます。完了済みIssueは現行仕様の根拠にせず、設計判断の確認が必要な場合
だけ参照します。

## 監査結果と移行順序

2026-07-27の棚卸しでは、ロードマップの現在地、開発参加入口、版固有情報と恒久手順の分離、
ADR規則、ローカルIssue参照、文書検査範囲に不足がありました。本変更で文書マップ、
`CONTRIBUTING.md`、Issue移行表、ロードマップ、リンク検査を整備しました。

読者別サブディレクトリへの大規模移動やMarkdownからAsciiDocへの一括変換は行いません。今後は
内容を変更する文書から冒頭要件と重複削減を適用し、必要性を確認できた移動だけを小さいPull Request
として実施します。
