= 文書管理方針

== 目的と対象

[#top]
この文書は、Marginalisの文書について対象読者、役割、優先して参照する資料、更新契機を定めており、
文書を作成・更新する際の基準として使用します。Marginalisの動作そのものは定義せず、
個別の仕様は xref:README.adoc#top[資料案内]から参照します。

== 文書冒頭の要件

現在の仕様や運用方法を定める新しい文書は、冒頭で対象読者、目的、対象外、優先して参照する範囲、
関連文書を説明します。短い案内文書では一つの段落へまとめても構いません。既存文書は内容を
変更するときにこの形式へ段階的に揃えます。バージョン番号付きsnapshotへ遡及的な書式変更は
行いません。

== 資料間の優先関係と不一致

システム要件は``requirements.adoc``、一貫して満たすべき設計条件は``architecture.adoc``、公開REST
APIの正式な仕様は``openapi.json``、MCP toolの入出力は``mcp-tools.json``、各項目の利用方法と
運用方法は詳細を定めた文書を正とします。
schema、manifest、コード上の定数は実装または配布物であり、確定した要件より優先しません。

要件、設計、公開仕様、実装が一致しない場合は、優先順位で一方を正しいことにせず欠陥として
記録します。意図した仕様を確認し、同じ変更で文書、プログラムが参照する仕様、実装、試験を
一致させます。
READMEなどの概要、ロードマップ、Issue、バージョン番号付きsnapshot、ヒアリング、研究文書は
現行仕様の代用にしません。

重複する説明は概要側を短くし、詳細を定めた資料へリンクします。プログラムが参照する仕様を文章にも
記載する場合は、その文章を仕様から生成するか、内容の一致を確認するテストを設けます。

== 情報種別の分離

* *現行仕様*: 現在の利用者・運用者向け動作と、一貫して満たすべき設計条件
* *設計判断*: 長期に参照する選択理由、代替案、再検討条件
* *将来計画*: ロードマップ上の方向、順序、公開単位
* *作業項目*: GitHub Issue上の背景、依存関係、動作例、完了条件
* *公開履歴*: GitHub ReleasesのRelease NotesとGit tag上の文書
* *現在の仕様として扱わない記録*: バージョン番号付きsnapshot、ヒアリング、研究上の考察

ADRを追加する場合は``docs/adr/NNNN-短い名称.adoc``とし、状態、日付、背景、決定、結果、代替案、
再検討条件を記載します。作業状況や一時的な計画はADRへ記載しません。

== AsciiDoc文書の規則

``AGENTS.md``を除く人間向け文書はAsciiDocで管理します
（ https://github.com/KeishiS/marginalis/issues/334[Issue \#334]で移行済み）。
新しいMarkdown文書は追加しません。

AsciiDoc文書はAdocWeave v0.36.0のstrict profileで解析し、local targetを検査します。文書間の``xref``は
参照先の``.adoc``と明示IDを指定します。明示IDの存在はAdocWeaveの構造化公開APIを使用する
``marginalis-documentation`` crateで検査します。traceabilityの表も、同じ公開APIが返す
``Table``、``TableRow``、``TableCell``から読み取ります。AsciiDocの構文規則は専用scriptへ書き写しません。自然文は
同じ版のtextlint Processorに同梱されたWebAssemblyで解析し、source blockやinline codeを校正対象から
除外します。

表の``cols``属性は、``cols="1,1,1"``のように列数と既定幅を明示します。空の列指定へ列数の意味を
持たせず、検査と描画がsemantic model上の同じ行と列を使用できる状態にします。

``xref:``と``link:``は、前の文章との間に空白を置き、AdocWeaveが記法として認識できる境界へ配置します。
通常の文章として残った記法らしい文字列は``marginalis-documentation``が拒否します。記法そのものを説明する
場合はinline codeとして記述します。内容を通常の解析に通さないpassthrough記法は、人間向け文書では
使用しません。

固定名が必要な``AGENTS.md``にはMarkdownのlink検査を適用します。traceabilityと観測event対応は
AsciiDocの構造に合わせて検査し、文書形式の変更で検査範囲を狭めません。

== 状態と用語

機能や仕様の状態には「対応」「非対応」「条件付き対応」「廃止」を使用します。「保持」はデータや
履歴の保存期間にだけ使用します。識別子、HTTP header、設定名、コマンド、コード上の型名は原綴りを
使い、それ以外は自然な日本語で説明します。

== Issueと履歴

作業項目はGitHub Issuesで管理します。リポジトリ内にIssueファイルを追加しません。v0.5.0以前の
ローカルIssueの原文は``v0.5.0``タグ上の``issues/``、GitHub Issueへの移行対応表は``v0.36.0``タグ上の
``docs/issue-migration.adoc``から辿れます。完了済みIssueは現行仕様の根拠にせず、設計判断の確認が
必要な場合だけ参照します。

== 監査結果と移行順序

2026-07-27の棚卸しでは、ロードマップの現在地、開発参加入口、特定のバージョンに固有の情報と
恒久手順の分離、ADR規則、ローカルIssue参照、文書検査範囲に不足がありました。本変更で
文書マップ、``CONTRIBUTING.adoc``、Issue移行表、ロードマップ、リンク検査を整備しました。

読者別サブディレクトリへの大規模移動は行いません。AsciiDoc化は内容の役割を変えず、小さいPull Requestへ
分けて実施します。各段階で、冒頭要件、重複削減、文書間参照の明示IDを確認します。
