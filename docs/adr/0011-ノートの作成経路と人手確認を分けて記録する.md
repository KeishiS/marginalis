# ノートの作成経路と人手確認を分けて記録する

- 状態: 採用
- 日付: 2026-08-05
- 関連Issue: #232

## 背景

Marginalisのノートには、どの接続方法から作成されたかと、現在の版を利用者が確認したかを記録する
項目がありません。この二つを一つの値にまとめると、MCP経由で作成した後に人が整えたノートと、
Web UIで作成したまま確認していないノートを区別できません。また、既存ノートには作成時の記録が
ないため、移行時に未確認または特定の作成経路だったと推測することもできません。

作成経路は接続方法の記録にすぎず、AIが作成したことの証明にはなりません。人手確認も内容が正しい
ことの保証ではなく、特定の版を利用者が明示的に確認した事実です。将来、機械学習用データを選ぶ際に
誤った意味で使われないよう、保存項目、権限、公開範囲を分けます。

## 決定

### 作成経路

ノートへ変更できない`created_via`を保存し、値を`web`、`rest`、`mcp`、`unknown`に限定します。
transport adapterがapplicationへこの値を渡し、ノート本文やAPIの入力項目からは指定させません。
Web UIと汎用REST APIはサーバー側で区別できる入口を使用します。MCP toolは`mcp`を使用します。

既存archiveから移行したノートは、根拠がないため`unknown`とします。作成経路は補助情報であり、
利用者またはクライアントの種類、AIの利用、内容の品質を証明しないことを公開資料に明記します。

### 人手確認の保存状態

保存状態は、過去の確認情報が分からない状態と、確認の有無を追跡し始めた状態を区別します。

- **不明**: 旧形式から移行し、過去に確認したか判断できない状態
- **確認待ち**: 確認を追跡しているが、現在のrevisionと一致する確認記録がない状態
- **確認済み**: 確認したrevisionが現在のrevisionと一致する状態

新しく作成したノートは確認待ちとします。旧形式から移行したノートは不明とし、未確認だったという
負の情報へ変換しません。一度利用者が確認操作を行った後は追跡済みとなるため、後の変更で確認待ちに
戻っても不明には戻しません。

確認記録には、確認したrevision、確認日時、確認者のOIDC issuerとsubjectを保存します。確認待ちへ
戻った後も最後の記録は監査情報として保持します。通常の一覧、REST API、MCPには、現在の状態、
確認したrevision、確認日時だけを返します。確認者の識別情報は、所有者向けの確認詳細とarchiveに
限定し、共有先やMCPクライアントへ開示しません。

### revisionとの関係

人手確認はノート全体のrevisionに対して行います。本文、ACL、削除、復元のいずれであってもrevisionが
変われば、以前の確認済み状態を現在の版へ引き継ぎません。ACLや削除状態は本文の内容を変えませんが、
確認対象を「本文だけの版」と「ノート全体の版」に分けると、更新時の競合検査と表示するrevisionの
意味が分かれます。確認範囲を一つに保ち、判断に迷う変更では安全側に倒して再確認を求めます。

確認操作は、読み取ったrevisionを指定する条件付き更新とします。同じtransaction内で所有者の
`Manage`アクセス、現在のrevision、削除されていない状態を確認し、すべて一致した場合だけ確認者と
時刻を保存します。共有先の`Edit`アクセスでは確認済みにできません。

### transportの境界

Web UIはノートの状態を表示し、所有者へ「現在の版を確認済みにする」操作を提供します。この操作は
Web session、同一origin、CSRF tokenを要求する専用REST endpointを使います。汎用REST APIの作成経路は
`rest`、Web UI専用の作成入口は`web`としてapplicationへ渡します。

MCPの一覧と個別取得は現在の確認状態と作成経路を返しますが、確認を設定するtoolは提供しません。
既存toolの入力JSON Schemaは未定義項目を拒否し、作成・更新入力から確認情報を受け取りません。

### 抽出と移行

REST APIとMCPのノート一覧は、`created_via`と現在の確認状態による任意の絞り込みを受け付けます。
SQLiteで閲覧認可と絞り込みを同じ問い合わせへ適用し、取得後のデータから隠す方式にはしません。
これは来歴を完全一致で抽出する境界です。全文検索、検索索引、順位付けはMarginalisへ追加せず、
[連環（Renkan）](../research-search-vision.md)が公開されたノート情報を検索用の投影へ取り込みます。

SQLite schemaとarchive形式を更新します。現行archiveからの移行では、ノート本文、ACL、日時、revisionを
維持し、作成経路と確認状態だけを不明として補います。現行形式のarchiveは作成経路、追跡済みかどうか、
最後の確認記録を保存し、隔離復元で同じ状態へ戻ることを検証します。

## 結果

接続方法と人手確認を独立して抽出でき、MCP経由のノートを人が後から確認した場合も情報を失いません。
確認後にどの変更経路からrevisionが進んでも、古い確認を現在の版へ誤って適用しません。既存ノートは
情報不足と未確認を区別したまま移行できます。

ACLや削除状態だけを変更した場合も再確認が必要になるため、所有者の操作は増えます。一方、確認対象の
revisionをAPIの更新番号と同じ意味に保てるため、本文用の別revisionや内容hashを追加せずに済みます。
作成経路と人手確認は証明ではないため、教師情報として使う側には用途に応じた追加の選別が必要です。

## 代替案

### `reviewed`の真偽値だけを保存する

確認後に本文を変更しても真のまま残り、どの版を確認したか判断できないため採用しません。

### 既存ノートを確認待ちとして移行する

過去の情報がない状態を、確認していないという負の情報へ変えてしまうため採用しません。

### ACLだけの変更では確認済み状態を維持する

本文用revisionを別に持つか、確認したrevisionと現在のrevisionが違っても確認済みと判定する必要が
あります。公開するrevisionの意味が分かれるため、最初の実装では採用しません。

### 編集権限を持つ共有先にも確認を許可する

共同確認には役立ちますが、所有者が教師情報として扱う印を共有先が変更できるようになります。
確認者の役割と取消方法を別途設計するまでは、所有者だけに限定します。

### 作成要求で`created_via`を受け取る

実装は単純ですが、クライアントが任意の経路を名乗れます。接続方法という意味を保つため、サーバー側の
入口で決めます。

## 再検討条件

- 本文とACLの更新頻度が大きく異なり、ACL変更後の再確認が運用上の負担になる場合
- 複数人による確認、確認の取消、二人以上の承認など、所有者一人では足りない手順が必要になった場合
- 確認者を共有先または外部の教師データへ開示する目的と、個人情報の保持期間が決まった場合
- 作成時に使われたAIや生成過程を証明する、署名付きの来歴規格を採用する場合
