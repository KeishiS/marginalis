# MCPのscope上限を利用者設定として管理する

- 状態: 採用
- 日付: 2026-08-04
- 関連Issue: #268
- 補足対象: [ADR 0008](0008-mcp-authorization-serverの中核を製品から分離する.md)

## 背景

Marginalisの内蔵Authorization Serverは、resourceが対応するscopeと、MCPクライアントが今回要求した
scopeを検査します。しかし、同じ利用者がすべてのクライアントへ同じ上限を適用するとは限りません。
例えば、利用者が書き込みを許可できる場合でも、文献を閲覧するだけのクライアントには読み取りだけを
許可したいことがあります。

利用者に許可する上限と、個別のMCPクライアントに許可する上限は異なる判断です。両者を一つの値として
保存すると、利用者全体の方針を変更した場合と、一つのクライアントだけを制限した場合を区別できません。
また、現在のMarginalisには、他人のOAuth権限を管理するサーバー管理者の役割がありません。

## 決定

ノート所有者が、自分のMCP認可に対する次の二種類のscope上限をMarginalisの設定画面で管理します。

- 利用者上限: その利用者がすべてのMCPクライアントへ許可できるscopeの最大集合
- クライアント上限: その利用者が特定の`client_id`へ許可できるscopeの最大集合

実際に同意画面へ示し、認可codeとtokenへ記録できるscopeは、次の共通部分に限定します。

```text
サーバー対応scope
∩ 利用者上限
∩ クライアント上限
∩ 今回の要求scope
∩ 利用者が同意画面で選んだscope
```

上限を超えるscopeは同意画面へ表示しません。送信内容を変更して上限外のscopeを指定した場合は、
暗黙に削るだけで認可を続けず、要求を拒否します。共通部分が空の場合も、`notes:read`などを自動的に
追加しません。

設定の保存と変更はMarginalisの責務とします。製品非依存の`mcp-authorization-server`は、二種類の
上限を区別して受け取り、対応scopeと要求scopeとの共通部分を正規の順序で計算します。Kanidmのclaimや
NixOSの配備設定を、利用者別またはクライアント別上限の正本にはしません。これらは運用者が一括配備する
設定であり、本人が接続先ごとに変更する用途と更新単位が異なるためです。

利用者は自分の上限だけを変更できます。この設定により、別の利用者のノート、ACL、認可へアクセスする
権限は得られません。scopeは操作の種類だけを制限し、ノートと書誌情報の所有者境界は従来の認可を
引き続き適用します。

上限を引き下げる変更は、保存と同じtransactionで次を無効にします。

- 利用者上限の変更: 新しい上限を超える、その利用者の認可codeとtoken family
- クライアント上限の変更: 新しい上限を超える、その利用者と`client_id`の認可codeとtoken family

発行済みaccess tokenの有効期限まで待ちません。上限を引き上げた場合は、既存の認可code、access token、
refresh tokenへscopeを追加せず、クライアントによる新しい要求と利用者の同意を必要とします。

v0.29.0へ更新した直後の既定値は、既存の接続を突然失効させないため、利用者上限とクライアント上限の
どちらもサーバー対応scopeとします。これはscopeを自動的に発行する設定ではありません。実際の発行範囲は
クライアントの要求と同意で引き続き狭められます。設定画面で上限を変更した時点から、新しい制限を即時に
適用します。

## 結果

利用者全体の方針と接続先ごとの方針を区別でき、上限を下げた後に古いtokenだけが広い権限を保つ状態を
避けられます。共有Authorization ServerはMarginalis固有のscope名や設定画面を知らず、別の利用製品も
同じ共通部分の計算を利用できます。

設定画面、保存形式、失効処理が必要になるため、v0.28系との互換性を保つパッチではなくv0.29.0として
公開します。同意時のscope選択、認可済みクライアントの一覧と取消、段階的な追加認可は、それぞれの
関連Issueでこの上限を参照して実装します。

## 代替案

**NixOSの配備設定だけで上限を管理する**: 運用者が一括して強制できますが、個々の利用者が接続先ごとに
変更できません。現在存在しない管理者権限も必要になるため採用しません。

**Kanidmのgroupまたはclaimから上限を決める**: 組織全体の役割には適しますが、MCPクライアントごとの
本人の判断を認証基盤へ持ち込みます。Marginalis単体で即時変更とtoken失効を完結できないため採用しません。

**利用者上限を設けず、クライアント上限だけを保存する**: 接続先ごとの制限はできますが、利用者が
すべての接続から削除操作を外すような全体方針を一か所で表せないため採用しません。

**上限変更後も発行済みtokenを期限まで有効にする**: 保存処理は単純になりますが、画面で制限した内容と
実際に可能な操作が一致しない期間が生じるため採用しません。

## 再検討条件

- 他の利用者の上限を管理する、明示的な運用者権限が必要になった場合
- Kanidm側の組織方針を、本人設定より狭い強制上限として適用する要件が生じた場合
- 一つの`client_id`を複数の信頼区分へ分ける、`client_id`以外の安定した識別方法が標準化された場合
- 独立したAuthorization Serverへ配備単位を変更し、設定とtokenの保存責任がMarginalisから移る場合
