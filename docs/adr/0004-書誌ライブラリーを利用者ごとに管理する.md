# 書誌ライブラリーを利用者ごとに管理する

- 状態: 採用
- 日付: 2026-07-30

## 背景

Issue #147では、利用者が取り込んだBibTeXの書誌情報を複数のノートから`cite:`で引用し、本文中の
引用と参考文献一覧を同じ規則で表示できるようにします。Web UI、REST API、MCPは同じ
書誌ライブラリーを使用し、将来はZoteroなどの文献管理ツールとの同期も想定します。

書誌情報をノート本文へ直接複製すると、同じ文献の修正をノートごとに繰り返す必要があります。
サービス全体で一つのライブラリーにすると重複は減りますが、誰が値を変更できるか、未公開の
研究対象をほかの利用者へ漏らさないか、同じcitation keyや異なる書誌情報をどう調停するかが
不明確になります。

引用済みノートは、書誌情報の更新や削除と同時に意味が変わる可能性があります。外部ツールとの同期で
citation keyが変わる場合も、ノートが別の文献を指さないようにする必要があります。

AdocWeaveでの`cite:`解析と安全なHTML生成は
[AdocWeave Issue #283](https://github.com/KeishiS/adocweave/issues/283)で設計中です。この記録では、
その公開契約に依存しない所有範囲、識別子、保存、競合、削除の規則を確定します。

## 決定

書誌ライブラリーは利用者ごとに管理します。最初の実装では所有者本人だけが項目を検索、追加、編集、
削除でき、利用者間の共有とサービス全体の共通項目は提供しません。

### 識別子

- 各書誌項目には、作成後に変わらない内部IDを割り当てます。REST API、MCP、引用関係、archive、
  外部同期の対応付けにはこのIDを使用します。
- citation keyは所有者のライブラリー内で一意とし、別の利用者との重複を許します。
- citation keyの変更は、同じトランザクションで参照中のノートを検査できる専用操作にします。
  内部IDは変更せず、別の文献への差し替えとして扱いません。
- DOI、ISBN、arXiv IDなどの外部IDは検索と重複候補の検出に使用します。外部IDだけで項目を
  上書きまたは削除しません。

### 保存内容

各書誌項目には、少なくとも次を保存します。

- 所有者、内部ID、citation key、revision
- 利用者が取り込んだBibTeXの項目原文
- BibTeXから取得した項目型、題名、著者、発行年、DOI、ISBN、arXiv IDなどの構造化値
- 取込元を識別する種類と、外部ツールが明示した不透明なID
- 作成日時と更新日時

構造化値は検索と組版に使用しますが、欠けた著者名、題名、発行年、識別子をMarginalisが推測して
補いません。BibTeX全体のファイルは一つの項目へ複製せず、項目ごとの原文と取込結果を保存します。
引用形式は検証済みの組込みスタイルを表す固定値としてノートに保存し、任意のCSLや`.bst`を
実行しません。

### 引用と競合

ノートには、引用した書誌項目の内部IDと、保存時に解決した書誌項目のrevisionを記録します。
`create_note`と`update_note`は、すべてのcitation keyを同じ利用者のライブラリーから解決し、
書誌項目のrevisionを再確認してから、ノート本文と引用関係を一つのトランザクションで保存します。

未登録、権限不足、不正な引用、またはrevision競合が一件でもある場合はノートを変更しません。
権限のない項目の存在は、未登録の場合と区別できる応答へ含めません。

参照中の書誌項目は削除を拒否します。削除要求には内部IDと期待するrevisionを必須とし、
citation keyや外部IDだけによる削除を許しません。項目の更新後に過去のノートrevisionを
再現する要件は、ノートの履歴保存と合わせて別途設計します。現行のノートrevisionは履歴そのものを
保存しないため、このIssueだけで過去の表示を再現できるとは扱いません。

### archiveと外部同期

archiveには書誌項目、所有者、原文、構造化値、revision、ノートからの引用関係、引用スタイルを
含めます。Webセッションや外部サービスの認証情報は含めません。archiveの読込時は、citation keyの
一意性、内部ID、所有者、引用先、revisionの対応を全件検査してから空のデータベースへ保存します。

外部同期では、外部サービス名と外部IDを対応付けに使用し、citation keyを恒久的なIDとして
扱いません。同期先の認証情報、同期の開始方法、競合解決は、実際に連携するサービスを選んだ時点で
別の設計記録へ定めます。

## 結果

利用者は一度登録した書誌情報を複数のノートから利用でき、ほかの利用者による変更やcitation keyの
衝突を受けません。REST API、MCP、Web UIは同じ所有者境界、内部ID、revisionを使用できます。
不変の内部IDと外部IDの対応を持つため、citation keyを変更できる設計でも外部文献管理ツールとの
同期を妨げません。

同じ文献を利用者ごとに保存する重複は許容します。共有ライブラリーを後から追加する場合は、所有者、
編集権限、個人用のタグと同期情報、引用済みノートへの影響を新しい公開契約として設計する必要が
あります。

## 代替案

### ノートごとにBibTeXを保存

ノート単体で持ち運べますが、同じ文献の修正と外部同期をノートごとに繰り返します。同じcitation keyが
ノートごとに別の書誌情報を指し、MCPが引用可能な文献を事前に検索できないため採用しません。

### サービス全体で一つのライブラリーを共有

重複を減らせますが、ある利用者の追加、修正、削除がほかの利用者のノートへ影響します。登録済みの
文献や引用関係から研究対象を推測されるおそれもあります。所有と共有の規則なしに導入できないため
採用しません。

### citation keyを内部IDとして使用

BibTeXや既存ツールとの対応は分かりやすくなりますが、citation keyの変更、利用者間の重複、
外部ツール側のキー変更によって参照が不安定になります。変更しない内部IDと分離します。

### 書誌項目の更新を既存ノートへ直ちに反映

常に最新の訂正を表示できますが、同じノートrevisionの表示が書誌項目の変更だけで変わります。
どの更新をノートへ反映するか利用者が判断できる操作と履歴の要件が未確定のため、最初の実装では
ノート保存時に解決した書誌revisionを記録します。

## 再検討条件

次のいずれかが具体的な利用例と権限要件を伴って必要になった場合に再検討します。

- 複数の利用者が同じ書誌項目を共同編集する必要性
- 組織が管理する読取り専用の共通書誌ライブラリーの必要性
- Zoteroなど採用する外部サービスの共有グループとMarginalisの所有者境界を対応させる必要性
- 過去のノートrevisionと当時の引用表示を再現する履歴保存の必要性
