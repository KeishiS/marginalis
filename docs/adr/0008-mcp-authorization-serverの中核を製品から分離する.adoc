= MCP Authorization Serverの中核を製品から分離する

[#top]
* 状態: 採用
* 日付: 2026-08-04
* 関連Issue: \#269
* 補足対象: xref:0007-mcpのauthorization-serverを内蔵する.adoc#top[ADR 0007]

== 背景

ADR 0007に基づく内蔵Authorization Serverは、MCPクライアントの登録、Authorization Codeと
PKCE S256、resourceとscopeの検査、不透明token、refresh token rotation、再利用時のtoken family失効、
取消を提供しています。配備はMarginalisの同一プロセスで完結し、利用者の本人確認だけをKanidm OIDCへ
委ねています。

一方、プロトコルの型と状態遷移は``marginalis-domain``と``marginalis-application``に置かれており、
ノートを扱うアプリケーションの型、固定した``notes:*`` scope、単一のresource、SQLite実装と結び付いて
います。別サービスで同じ安全性を満たすMCP認可が必要になった場合、この構造では処理を複製するか、
Marginalisを別サービスの認可主体として扱うことになります。

xref:../research-search-vision.adoc#top[連環（Renkan）]はMarginalisの機能ではなく、複数の研究資料を対象とする
別の探索サービスです。MarginalisとRenkanで利用者の認証基盤を共有しても、resource、scope、token、
grant、保存先は混在させません。

== 決定

MCP Authorization Serverの中核を、製品非依存のworkspace crate
``mcp-authorization-server``へ分離します。独立配布を決定するまでは、このcrateをMarginalisリポジトリに置き、
Marginalisの同一プロセスへ組み込みます。独立したdaemon、ネットワーク越しのtoken introspection、
外部Authorization Serverとの切替は導入しません。

最初から複数のcrateへ細分化せず、次の責務を一つのcrate内のmoduleとして分けます。

* ``protocol``: OAuthの要求、応答、client、resource、scopeを表す公開型と検査
* ``core``: 認可code、token発行、refresh rotation、認証、取消の状態遷移
* ``repository``: 原子的な保存操作を表すport
* ``client_metadata``: CIMDによるclient解決を表すportと共通のmetadata検査

crateを分けなければ依存方向を守れない状態になった場合だけ、moduleを独立crateへ分けます。
``mcp-authorization-server``はAxum、SQLx、Kanidm、``marginalis-*``、``renkan-*``へ依存しません。
この原則に従い、CIMDの外部取得だけは``mcp-authorization-server-cimd``へ分けます。CIMDはHTTP client、
非同期の同時実行制御、DNS名前解決を必要としますが、中核の状態遷移とmetadata検証は必要としません。
別crateにすることで、中核へ``reqwest``と``tokio``を持ち込まず、別のHTTP adapterへの交換も可能にします。

中核へ渡す主体は、検証済みのissuerとsubjectだけを持つ``Principal``とします。Kanidmとの通信、
group検査、Web session、Cookie、CSRF、同意画面はMarginalisに残します。中核が認証基盤や利用者向け
画面を直接扱うことはありません。

resource URI、表示名、対応scope、既定scope、token寿命、認可code寿命、client登録上限は
``ResourcePolicy``とAuthorization Serverの設定から与えます。metadata、認可要求、token更新、
Bearer tokenのchallengeは同じpolicyから導出します。``notes:*``とMCP toolの対応、ノートの所有者・ACLは
Marginalis側の責務です。

repository portはテーブルごとのCRUDではなく、次の原子的な操作を表します。

* 認可codeの保存
* 認可codeの一回消費と最初のtoken pair発行
* refresh tokenの一回消費と次のtoken pair発行
* 使用済みrefresh tokenの検出とtoken family全体の失効
* 利用者とclientの組合せによるgrant取消
* token単位の取消
* 上限を含むclient登録

SQLite adapterはMarginalisに残し、既存schemaと保存値を維持します。中核が提供する同じrepository
契約試験を、特定のdatabaseへ依存しない試験用repositoryとSQLite adapterの両方へ適用します。
これにより、期限の境界、codeとtokenの一回消費、token familyの失効、resource binding、取消が
保存方法によって変わらないことを検査します。PostgreSQL adapterとRenkanへの統合はRenkan側で管理します。

移行は次の順で行います。

[arabic]
. 製品非依存の型、設定、repository port、状態遷移をworkspace crateへ移します。
. Marginalisのapplication境界で``Actor``と``Principal``を変換します。
. 既存SQLite adapterを新しいrepository portへ接続します。
. HTTP endpoint、同意画面、MCP tool認可をMarginalis側に維持したまま、中核から結果を受け取ります。
. CIMD resolverと安全上の上限を製品非依存のmoduleへ移します。
. 既存のSQLite、HTTP、NixOS E2E、実クライアント試験で外部動作が変わらないことを確認します。

== 結果

OAuthの安全性に関わる状態遷移を一か所で保守でき、Marginalis固有のノート操作を読み解かずに試験できます。
Marginalisは引き続き内蔵Authorization Serverを配備するため、運用方法と即時取消の性質は変わりません。

crateの外部公開APIと配布方法は、workspace内の境界とrepository契約試験を確認した後に
https://github.com/KeishiS/marginalis/issues/314[Issue 314]で決定します。独立リポジトリ、registry、固定した
Git dependencyを比較し、不安定な公開APIを複数の利用側で早期に固定することは避けます。現在の版管理と
更新手順は xref:../mcp-authorization-server-maintenance.adoc#top[保守文書]に記載します。

== 代替案

*直ちに独立リポジトリへ移す*: 製品間で中立な所有場所を作れます。しかし、現在の型はMarginalis固有の
責務と結び付いており、移動とAPI設計を同時に行うと、修正のたびに複数リポジトリの変更が必要になります。
まずworkspace内で境界を検証するため採用しません。

*独立したAuthorization Server daemonにする*: 複数サービスから一つの配備を利用できますが、tokenを
共有しない要件に対して運用、鍵、可用性、introspection通信を追加します。現在は同一プロセスによる即時の
認証と取消で要件を満たすため採用しません。

*Marginalisのapplication層をそのまま共有する*: 移動量は少なくなりますが、ノートのdomain型、
``notes:*``、SQLiteへの依存が残り、別サービスがMarginalisへ依存します。所有関係を改善できないため
採用しません。

*初めからprotocol、core、HTTP、databaseごとにcrateを分ける*: 境界は明示されますが、公開APIと
versionの組合せが増えます。まずmoduleで依存方向を検査し、独立して更新する根拠が得られた部分だけを
分けます。

== 再検討条件

* Marginalis以外の利用側が、検証済みの中核crateを実際に必要とする場合
* crateのmodule間で循環依存が生じ、一つのversionで管理することが変更を妨げる場合
* 独立した脆弱性対応と公開周期がMarginalisの公開周期より必要になった場合
* 複数サービスでtokenを共有する運用要件が生じ、同一プロセスの組込みでは満たせない場合
* MCPまたはOAuth仕様の変更により、現在の限定したAuthorization Code構成を維持できない場合
