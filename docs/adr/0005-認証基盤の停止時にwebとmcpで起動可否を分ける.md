# 認証基盤の停止時にWebとMCPで起動可否を分ける

> MCPに関する決定は[ADR 0006](0006-mcpのauthorization-serverを内蔵する.md)で置き換えました。

- 状態: 採用
- 日付: 2026-07-30

## 背景

Marginalisは起動時に二つの認証基盤へ接続します。Web UIのログインにはKanidmのOIDC discovery、
MCPにはAuth0のAuthorization Server MetadataとJWKSです。どちらも外部サービスであり、一時的に
応答しないことがあります。

`marginalis-service`のcomposition rootは、この二つを異なる方針で扱っています。

- Kanidmのdiscoveryに失敗した場合は警告を記録し、`None`のまま起動を続けます。
- Auth0のdiscoveryに失敗した場合は起動そのものを失敗させます。

この違いは実装に現れているだけで、理由がコードにも文書にも書かれていませんでした。将来どちらかへ
そろえたくなったときに、意図的な設計だったのか実装の揺れだったのかを判断できません。

## 決定

この非対称を意図的な設計として維持し、理由を記録します。

**Kanidmのdiscoveryが失敗しても起動します。** ログインは失敗しますが、既にセッションを持つ利用者の
閲覧と編集、REST API、保守コマンド、バックアップは動作します。ログインできない状態と、サービス全体が
停止する状態では、後者のほうが影響が大きいと判断します。ログイン要求はfail closedで拒否するため、
認証を迂回する経路は生まれません。

**Auth0のdiscoveryが失敗した場合は起動しません。** MCPのaccess token検証にはAuth0のJWKSが必要です。
JWKSを取得できないまま起動すると、tokenを検証できないMCP endpointが公開されます。検証できない
requestはすべて拒否されるため実害は出ませんが、認証基盤なしでMCPを公開している状態を作らない方針を
優先します。

## 結果

`docs/nixos.md`は運用者向けにこの違いを説明します。監視では、Kanidmのdiscovery失敗を
`oidc.discovery.failed`で検知します。この状態はサービスが動作したままログインだけができないため、
起動失敗より気付きにくく、明示的な監視が必要です。

## 代替案

| 選択肢 | 評価 |
| --- | --- |
| 両方で起動を失敗させる | Kanidmの一時的な停止でサービス全体が落ちる。既存利用者の閲覧と編集、バックアップまで止まるため不採用 |
| 両方で起動を続ける | 検証できないMCP endpointを公開する状態が生まれる。実害は出ないが、認証基盤なしで公開しない方針に反するため不採用 |
| 起動後に再取得を繰り返す | Kanidm側は次回ログイン時に再取得するため既に同等である。Auth0側は起動時取得を維持し、実行中の未知の`kid`に対してだけ再取得する現在の実装で足りる |

## 再検討条件

- MCPを無効にしたまま運用する構成が主になり、Auth0の停止で起動できない不便が上回った場合
- Kanidmのdiscovery失敗を検知できず、ログインできない状態が長時間続く運用事故が起きた場合
- 起動時ではなく要求ごとにJWKSを取得する方式へ変更した場合
