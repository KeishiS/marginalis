## 今回の確認で重点を置いた点

内蔵Authorization Serverの中核を製品非依存のworkspace crateへ分離しました。認可code、PKCE S256、
resourceとscopeの検査、token発行、refresh token rotation、token familyの失効、取消について、
Marginalisのノート用ドメイン型、Kanidm、Axum、SQLxへ依存せずに同じ状態遷移を実行できることを
確認します。別のresource用に構成した中核がMarginalisのtokenを受理しないことも確認します。

Protected Resource Metadata、Authorization Server Metadata、認可要求、token更新、Bearer tokenの
challengeが同じresource policyから導出されることを確認します。DCRでは`application_type`を受理して
登録応答へ反映し、CIMDでは従来と同じHTTPS、SSRF対策、cache、取得上限を維持することを確認します。

公開MCP URL、`notes:*` scope、token寿命、SQLite schema、archive形式は変更していません。既存のclient
登録と発行済みtokenを維持したまま更新できることをNixOS VMで確認し、ChatGPT、Claude Code、Codex CLIで
metadataの発見、client登録、Kanidmへのログイン、同意、読み書き、取消、再認可を確認します。

利用者、Cookie、token、認可code、PKCE verifier、実際のノート本文や書誌情報は記録しません。
